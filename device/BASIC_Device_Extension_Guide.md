# 第1章 概要

## 1.1 BASIC のデバイスとは

MSX-BASIC では、ファイル入出力の相手を「デバイス」と呼ぶ。`OPEN "CAS:DATA1" FOR INPUT AS #1` のように、ファイルスペックの先頭にデバイス名を書くことで、カセット、画面、プリンタといった入出力先を指定する。BASIC に最初から組み込まれているデバイスには、次のようなものがある。

|デバイス名|相手|
|-|-|
|CAS:|カセットテープ|
|CRT:|テキスト画面|
|GRP:|グラフィック画面|
|LPT:|プリンタ|

ディスクドライブ（A:、B: など）もデバイスの一種として扱われるが、これはディスクインターフェイス側の仕組みで BASIC とつながっており、本書の主題であるカートリッジの DEVICE 機構とは経路が異なる（6.4 節）。

これらに加えて、ROM カートリッジが新しいデバイスを BASIC に追加できる。それが本書の主題である。カートリッジは、ROM ヘッダの DEVICE フィールドにデバイス拡張ルーチンのアドレスを登録しておく。すると BASIC は、自分の知らないデバイス名に出会ったとき、そのルーチンに「これはあなたのデバイスですか」と問い合わせて回り、引き受けたカートリッジのルーチンに以後の入出力を委ねる。RS-232C インターフェイスの COM: デバイスは、この機構で提供されるデバイスの代表例として知られている。

## 1.2 仕組みの全体像

デバイス拡張のやり取りは、大きく 2 つの段階に分かれる。

|段階|いつ起きるか|何をするか|
|-|-|-|
|識別（第3章）|BASIC が未知のデバイス名を解釈したとき|デバイス名を PROCNM（FD89H）に置き、A = FFH で各カートリッジのデバイスルーチンを順に呼ぶ。自分のデバイスだと名乗り出たカートリッジが、そのデバイスの担当になる|
|操作（第4章）|OPEN、CLOSE、PRINT #、INPUT # などの実際の入出力のとき|担当カートリッジのルーチンを、A = 要求コード、ワークエリア DEVICE（FD99H）= 装置 ID で呼ぶ。ルーチンは要求コードごとに決められた処理を行う|

識別に成功すると、BASIC はそのファイルを管理するためのファイルコントロールブロック（第5章）を 1 つ割り当て、ファイル番号と結び付ける。以後の操作は、すべてこのブロックを介して行われる。ファイル番号やバッファの管理は BASIC 側の仕事であり、デバイスルーチンは「要求された操作を、そのデバイスなりに実行する」ことに専念する。

この分担が、この機構の要点である。デバイスルーチンの作者は、BASIC のファイル文法（OPEN のモード指定、PRINT # の書式、EOF 関数の意味など）を再実装する必要はない。決められた要求コードとレジスタ規約に応答するだけで、BASIC のファイル入出力の全機能が自分のデバイスでも使えるようになる。

## 1.3 本書の立場と資料について

本書は、次の資料に基づいて記述している。

1. MSX-Datapack（アスキー）— 一次資料。カートリッジヘッダと DEVICE の枠組みは Vol.2 第5部第3章、起動時の走査は Vol.1 第1部、ファイルコントロールブロックの構造は Vol.1 第2部に基づく。
2. MSX Wiki の「Develop a program in cartridge ROM」— 操作フェーズのレジスタ詳細は Datapack に記載が乏しいため、この資料で照合した。Datapack が公表しているファイルコントロールブロックのレイアウトと、フィールド単位で整合することを確認している。
3. 実物の SUB ROM のコード — MSX2+ の SUB ROM には、メモリディスク（MEM）を DEVICE 機構で提供する実装が含まれている。その入口の構造（識別の作法や要求の振り分け方）を読み、資料の記述と突き合わせた（3.5 節、付録 A.2）。

資料で裏が取れない事項は、推測で埋めずに「未確認」と明記した。特に、要求コード 16（FPOS）と 18（バックアップ）については、要求の存在と名称は確定しているが、入出力の詳細は入手できる資料に記載がない（4.10 節、付録 A.3）。また、識別成功時に返す装置 ID の範囲は、Datapack の記述（0〜3）と MSX Wiki の記述（1〜4）が食い違う。本書は一次資料である Datapack の記述を採用し、SUB ROM の実装が ID = 0 を返すこともその傍証とした（付録 A.3）。

Datapack 自身が注意を促しているとおり、デバイス拡張は MSX の内部システムに関する深い知識を要する仕組みである。本書は、その「深い知識」のうち、デバイスルーチンを書くために必要な部分——ヘッダ、識別、要求、ファイルコントロールブロック——を 1 か所に集めることを目的としている。

# 第2章 カートリッジヘッダと登録

## 2.1 カートリッジヘッダの構成

MSX の ROM カートリッジは、16 バイトの共通ヘッダを持つ。ヘッダは 4000H または 8000H を先頭として配置され、システムはリセット時にこのヘッダを見てカートリッジの初期設定を行う。

|変位|名称|内容|
|-|-|-|
|+0000H|ID|ROM カートリッジであることを示す 2 バイト。「AB」（41H、42H）を入れる。なお SUB ROM の ID は「CD」である|
|+0002H|INIT|初期化ルーチンのアドレス。行わなければ 0000H|
|+0004H|STATEMENT|ステートメント拡張ルーチンのアドレス（CALL 文の拡張）。行わなければ 0000H|
|+0006H|DEVICE|デバイス拡張ルーチンのアドレス。行わなければ 0000H|
|+0008H|TEXT|ROM 内 BASIC プログラムのテキストポインタ。行わなければ 0000H|
|+000AH〜|（予約）|システム予約領域。00H で埋めておく|

デバイス拡張を行うカートリッジは、DEVICE フィールドにデバイス拡張ルーチンのアドレスを書き込む。それ以外のフィールドは、使うものだけを設定し、残りは 0000H にしておく。

## 2.2 DEVICE フィールド

DEVICE フィールドに関する規則は、次のとおりである。

- デバイス拡張ルーチンは、**4000H〜7FFFH のページになければならない**。STATEMENT 拡張ルーチンと同じ制約である。
- 1 つのカートリッジが持てるデバイスは、**最大で 4 つ**までである。どのデバイスを引き受けるかの区別は、ルーチン自身が識別の段階で行う（第3章）。
- 拡張デバイス名は、**15 文字以下**でなければならない。

起動時、DEVICE フィールドのルーチンが呼ばれることはない。呼ばれるのは、BASIC が未知のデバイス名を解釈したときだけである（第3章）。初期化が必要なら INIT ルーチンで行う。

## 2.3 起動時の走査と SLTATR

システムは起動時に、スロット番号の若い順に各スロットの 4000H、8000H を調べ、ROM ID（「AB」）が書かれているかどうかを確認する。ID が見つかれば、まず INIT が 0 以外の場合にそのルーチンをインタースロットコールする。続いて STATEMENT、DEVICE、TEXT の各フィールドを調べ、0 以外であったものについて、ワークエリア SLTATR（FCC9H〜FD08H）の対応するビットをセットする。

|フィールド|SLTATR のビット|
|-|-|
|STATEMENT|ビット 5|
|DEVICE|**ビット 6**|
|TEXT|ビット 7|

SLTATR は、スロット×ページごとに 1 バイトが割り当てられた表で、「そのスロットに何の拡張があるか」を BASIC が後から参照するための台帳である。BASIC がデバイス名の担当を探すときは、このビット 6 が立っているカートリッジだけが候補になる。つまり、DEVICE フィールドにアドレスを書くことと、SLTATR のビット 6 が立つことは対になっており、ROM カートリッジではシステムが自動的に行う。

なお、SUB ROM は通常のカートリッジと同様に INIT、STATEMENT、DEVICE の各エントリを持つが、TEXT エントリは持つことができない（3.5 節の実装例は、この SUB ROM のものである）。

## 2.4 候補の呼び出し順序

識別でも操作でも、関係するカートリッジへの制御の移し方は一貫している。

- 候補は、**スロット番号の小さい方から順**に呼ばれる。
- 識別の段階で「自分のデバイスではない」と答えたカートリッジは、そのデバイスについては以後の操作にも関与しない。担当は、識別で名乗り出た 1 つのカートリッジに固定される。
- 呼び出しはインタースロットコールで行われる。ルーチンは自分のスロットが選択された状態で実行されるので、自分の ROM 内のコードやデータをそのまま参照できる。

# 第3章 デバイスの識別

## 3.1 識別呼び出しの入力

BASIC インタープリタが、組み込みデバイスにもディスクにも当てはまらないデバイス名を見つけると、識別の手続きが始まる。たとえば `OPEN "NAME:ABC.TXT"` を実行したときの「NAME」がそれである。

インタープリタは、デバイス名をワークエリア **PROCNM（FD89H、16 バイト）** に格納する。名前は 00H で終わる文字列として置かれる。続いて、**A レジスタに FFH を入れて**、DEVICE フィールドが 0 以外のカートリッジ（SLTATR のビット 6 が立っているもの）を、スロット番号の小さい方から順に呼び出していく。

|項目|設定|
|-|-|
|A レジスタ|FFH（識別呼び出しであることの印）|
|PROCNM（FD89H）|照会中のデバイス名（00H 終端）|

A = FFH は、操作フェーズのどの要求コード（0〜18 の偶数）とも重ならないため、ルーチン側はこの値で「識別か操作か」を判別できる。実物の実装でも、入口で A が FFH かどうかを最初に判定する形になっている（3.5 節）。

## 3.2 応答の作法

呼ばれたデバイスルーチンは、まず PROCNM のデバイス名が自分の担当するものかどうかを調べ、結果をキャリーフラグで返す。

|場合|応答|
|-|-|
|自分のデバイスではない|**キャリーフラグを 1 にしてリターンする**。インタープリタは次のカートリッジを呼ぶ|
|自分のデバイスである|必要な処理を行い、**装置 ID（0〜3）を A レジスタに設定し、キャリーフラグを 0 にしてリターンする**。このカートリッジが担当に決まる|

装置 ID は、1 つのカートリッジが複数のデバイスを持つ場合に、それらを区別するための番号である。操作フェーズでは、この ID がワークエリア DEVICE（FD99H）に入れて渡されるので（4.1 節）、ルーチンは FD99H を見て「自分のどのデバイスに対する操作か」を判断できる。

自分のデバイスでない場合に他のレジスタやワークエリアをどう扱うべきかは、Datapack の DEVICE の項には明記がない。STATEMENT 拡張の項には「自分の処理すべきものでなかった場合は HL レジスタの変更はせず」と明記されており、識別の作法としては、レジスタ類をなるべく壊さずに CY = 1 で返すのが安全である。

## 3.3 誰も応答しなかった場合

すべてのカートリッジが最後までキャリーフラグ 1 で返した場合、そのデバイス名は誰のものでもないことになる。インタープリタは **"Bad file name"** エラーを表示して、文の実行を止める。タイポや、デバイスを提供するカートリッジの挿し忘れは、この形で現れる。

## 3.4 チャンネルバッファの割り当て

識別に成功すると、インタープリタはそのファイルのために、ファイルコントロールブロック（第5章）を 1 つ割り当てる。ブロックの大きさは 1 ファイルあたり 10BH（267 バイト）で、同時に開けるファイルの数は MAXFILES 文で決まる。このブロックへのポインタが、操作フェーズで毎回 HL レジスタに入れて渡される「I/O チャンネルポインタ」である。

ブロックの確保と解放、ファイル番号との結び付けは、すべてインタープリタの仕事である。デバイスルーチンがメモリを確保する必要はない。ルーチンがブロック内に保存してよいのは、自分のデバイスの状態（第5章）だけである。

## 3.5 実装例： SUB ROM のメモリディスク

MSX2+ の SUB ROM には、メモリディスクを DEVICE 機構で提供する実装が実在する。`CALL MEMINI` でメモリディスクを初期化すると、`OPEN "MEM:ファイル名"` が使えるようになる、あの機能である。SUB ROM のヘッダは、DEVICE フィールドにこのルーチンのアドレスを持っている（FS-A1ST 系で 36B4H、FS-A1WSX / HB-F1XDJ 系で 3658H）。

その入口の構造は、本章で述べた規約の教科書どおりである。

1. 入口で A を判定する。FFH なら識別、それ以外なら操作の振り分けへ進む。
2. 識別では、PROCNM（FD89H）と自分の持つデバイス名テーブルを 1 文字ずつ照合する。テーブルに置かれた名前は "MEM0" で、00H で終わっている。
3. 名前が一致すれば、キャリーフラグを 0 にして戻る。このとき A は 0 のままであり、**装置 ID = 0** として返される。不一致なら、キャリーフラグを 1 にして戻る。
4. 操作では、要求コードを添字とするジャンプテーブルで処理を振り分ける。テーブルには要求 0、2、4、……、18 に対応する **ちょうど 10 本** のハンドラが並んでいる（4.2 節の要求一覧と一致する）。

カートリッジの形をしていない SUB ROM であっても、仕組みそのものは同じ DEVICE 機構であり、ヘッダへの登録、識別、操作という流れが実物で確認できる好例である。

# 第4章 操作リクエスト詳説

## 4.1 共通の呼び出し規約

識別で担当が決まったデバイスに対して、実際の入出力は「要求」という形で伝えられる。インタープリタは、ワークエリア **DEVICE（FD99H）に装置 ID（0〜3）** を、**A レジスタに要求コード** を設定して、デバイスルーチンを呼び出す。

各要求に共通する入力として、**HL レジスタには I/O チャンネルポインタ**——そのファイルのファイルコントロールブロック（第5章）へのポインタ——が入る。ルーチンはこのブロックに自分の状態を保持し、後続の呼び出しでは同じブロックを受け取ることで、ファイルごとの文脈をたどる。

|項目|設定|
|-|-|
|A レジスタ|要求コード（0〜18 の偶数）|
|DEVICE（FD99H）|装置 ID（0〜3）。識別のときに返した値|
|HL|I/O チャンネルポインタ（ファイルコントロールブロック）|

## 4.2 要求コード一覧

要求コードは Datapack の表5.1 に定められた 10 種である。SUB ROM の実装でも、ちょうどこの 10 本分のハンドラが用意されていることを確認している（3.5 節）。

|A|要求|呼ばれる場面|
|-|-|-|
|0|OPEN|OPEN 文（および LOAD / SAVE）の実行時|
|2|CLOSE|CLOSE 文の実行時|
|4|ランダムアクセス|GET # / PUT # の実行時|
|6|シーケンシャル出力|PRINT # の実行時|
|8|シーケンシャル入力|INPUT # などの実行時|
|10|LOC 関数|LOC(#n) の評価時|
|12|LOF 関数|LOF(#n) の評価時|
|14|EOF 関数|EOF(#n) の評価時|
|16|FPOS 関数|FPOS 関数の評価時（詳細は未確認、4.10 節）|
|18|バックアップ|詳細は未確認（4.10 節）|

以下、各要求の入出力を述べる。4.3〜4.9 節のレジスタ詳細は、MSX Wiki のカートリッジ ROM 解説を Datapack の記述と照合したものである。

## 4.3 OPEN（A = 0）

OPEN 文の実行に伴って呼ばれる。ファイル名やモードは、ワークエリアとレジスタで渡される。

|項目|内容|
|-|-|
|D|デバイスコード|
|E|オープンモード（下表）|
|FILNAM（F866H）|要求されたファイル名|
|DAC+2（F7F8H）|ファイル番号（#n の n）|
|HL|I/O チャンネルポインタ|

オープンモードの値は次のとおりで、ファイルコントロールブロックの FL.MOD にもこの値が入る。

|値|モード|意味|
|-|-|-|
|0|CLOSED|閉じている（オープンされていない）|
|1|INPUT|入力用に開く|
|2|OUTPUT|出力用に開く（既存のファイルは上書き）|
|4|RANDOM|ランダムアクセス用に開く|
|8|APPEND|追加出力用に開く（ファイルポインタは末尾）|

ルーチンは、オープンに成功したら、結果を HL の指すブロックに格納して戻る。格納すべき項目は次のとおりである。

|位置|格納する内容|
|-|-|
|HL[0]|オープンモード（E で渡された値）|
|HL[1]、HL[2]|後続の呼び出しでこのファイルを識別するための値。ディスクファイルでは、この位置（FL.FCA / FL.LCA）に BDOS 用 FCB へのポインタが入る（5.1 節）|
|HL[4]|デバイスコード（D と同じ値）|

なお、インタープリタは PTRFIL（F864H）を現在のチャンネルポインタに設定してから処理を進める。オープンに失敗した場合は、4.11 節の方法で BASIC のエラーを起こす。

## 4.4 CLOSE（A = 2）

CLOSE 文の実行に伴って呼ばれる。入力は HL = I/O チャンネルポインタのみで、ブロックにはそのファイルを識別する情報がすべて入っている。クローズに成功したら、**HL[0] に 0 を書いて**（モード = CLOSED）戻る。失敗した場合は 4.11 節の方法でエラーを起こす。

## 4.5 ランダムアクセス（A = 4）

GET #n / PUT #n の実行に伴って呼ばれる。

|項目|内容|
|-|-|
|HL|I/O チャンネルポインタ|
|DE|「#n」の次の文字を指す BASIC テキストポインタ|
|B|00H = GET、80H = PUT|

レコード番号は、DE の指す BASIC テキストを解釈して得る。また、レコードの読み書き先バッファの位置は、フック H.FIEL のハンドラを実装することで知ることができる。処理が終わったら、HL に更新したテキストポインタを入れて戻る。失敗した場合は 4.11 節の方法でエラーを起こす。

## 4.6 シーケンシャル出力（A = 6）

PRINT # の実行に伴って、出力する文字が **C レジスタ** に入れて呼ばれる。ルーチンはその 1 文字をデバイスへ出力（または自分のバッファへ保存）する。失敗した場合は 4.11 節の方法でエラーを起こす。

## 4.7 シーケンシャル入力（A = 8）

INPUT # などの実行に伴って呼ばれる。ルーチンは 1 文字を読み取り、**A レジスタにその文字を入れ、キャリーフラグを 0 にして**戻る。読み取る文字がもう無い（ファイルの終わり）場合は、**キャリーフラグを 1 にして**戻る。

## 4.8 LOC / LOF（A = 10 / 12）

LOC(#n)、LOF(#n) 関数の評価に伴って呼ばれる。入力は HL = I/O チャンネルポインタである。結果は、関数の戻り値として次の形で返す。

|項目|設定|
|-|-|
|DAC+2、DAC+3（F7F8H、F7F9H）|16 ビットの整数値。LOC は現在のファイル位置（シーケンシャルでは読み書き位置、ランダムでは最後に GET / PUT したレコード番号）、LOF はファイルの大きさ（バイト数）|
|VALTYP（F663H）|2（整数型であること）|

## 4.9 EOF（A = 14）

EOF(#n) 関数の評価に伴って呼ばれる。入力は HL = I/O チャンネルポインタである。ファイルの終わりに達しているかどうかを、次の形で返す。

|状態|DAC+2、DAC+3|VALTYP|CY|A|
|-|-|-|-|-|
|終わりではない|0|2|0|1|
|終わりである|FFH、FFH（−1）|2|1|0|

## 4.10 FPOS（A = 16）とバックアップ（A = 18）

要求コード 16 は FPOS 関数、18 は「バックアップ」と呼ばれる要求である。どちらも、存在と名称は Datapack の要求一覧に明記されている。しかし、その入出力の詳細は、Datapack にも照合資料にも記載がなく、本書では**未確認**として切り分ける。

手がかりは乏しい。FPOS は、MSX-DOS2 世代の BASIC にあるファイル位置関数であり、LOC と同様に DAC へ値を返す形が予想されるが、裏付けはない。バックアップについては、ファイルコントロールブロックに FL.LSA「バックアップキャラクタ」という領域があること（5.1 節）から、シーケンシャル入力で読み過ぎた 1 文字を押し戻す仕組みに関係すると推測されるが、これも推測の域を出ない。実装する場合は、この 2 つの要求には応答を用意せず、実機での検証を経てから扱うべきである。なお SUB ROM の実装では、この 2 つにもハンドラが割り当てられている（3.5 節）。

## 4.11 エラーの起こし方

デバイスルーチンの中で BASIC のエラーを起こしたいときは、BASIC 本体のエラー処理ルーチンをインタースロットコールする。

|項目|設定|
|-|-|
|E|エラー番号|
|HL|現在のテキストポインタの値|
|呼び出し先|BASIC の 406FH 番地（インタースロットコール）。BIOS の CALBAS（0159H）経由で呼ぶと安全である|

たとえば OPEN でファイルが見つからない、といった事態は、この方法で "File not found" などの BASIC エラーとして報告する。エラー番号は BASIC のエラーコード体系に従う。

# 第5章 ファイルコントロールブロック

## 5.1 構造

ファイルコントロールブロック（以下、ブロック）は、開かれているファイル 1 つ分の管理情報を収める領域である。BASIC インタープリタがファイルごとに確保し、その大きさは **10BH（267 バイト）** である。操作フェーズで HL に渡される I/O チャンネルポインタは、このブロックの先頭を指す。

|変位|ラベル|意味|
|-|-|-|
|+0|FL.MOD|ファイルがオープンされたモード（4.3 節の値）|
|+1|FL.FCA|BDOS 用 FCB へのポインタ（下位バイト）|
|+2|FL.LCA|BDOS 用 FCB へのポインタ（上位バイト）|
|+3|FL.LSA|バックアップキャラクタ|
|+4|FL.DSK|デバイスナンバー|
|+5|FL.SLB|意味は未確認（Datapack の記述が判読できなかった。付録 A.3）|
|+6|FL.BPS|FL.BUF の位置|
|+7|FL.FLG|いろいろな情報を持つフラグ|
|+8|FL.OPS|仮想的なヘッドの位置|
|+9〜|FL.BUF|ファイルバッファ（256 バイト）|

この構造はもともとディスクファイルのために定められたもので、ラベルの多くはディスク寄りの意味を持つ。カートリッジのデバイスでは、インタープリタが用意した枠組みをそのまま借りて使うことになる。

## 5.2 デバイスルーチンが触るフィールド

ブロックの所有者はインタープリタであり、デバイスルーチンが書き込むのは、OPEN の成功時に決められた項目に限られる（4.3 節）。

|位置|デバイスルーチンの関わり|
|-|-|
|HL[0]（FL.MOD）|OPEN でモードを書き込む。CLOSE で 0 に戻す|
|HL[1]、HL[2]（FL.FCA / FL.LCA）|OPEN で、後続の呼び出しでファイルを識別するための値を書き込む。自分のデバイスでファイルを識別する鍵として使う|
|HL[3]（FL.LSA）|バックアップキャラクタの置き場。シーケンシャル入力で 1 文字を押し戻す際に使われる領域とされる（要求コード 18 との関係は未確認、4.10 節）|
|HL[4]（FL.DSK）|OPEN でデバイスコードを書き込む|

FL.BUF（256 バイトのファイルバッファ）や FL.BPS、FL.OPS は、主にインタープリタとディスク処理が使う領域である。デバイス固有の大きなバッファが要る場合は、ブロック内に無理に押し込まず、自分のワークエリア（6.3 節）に確保するのが安全である。

## 5.3 MAXFILES とバッファの所有権

同時に開けるファイルの数は、MAXFILES 文で指定される（リセット時の既定は 1）。この数だけブロックが確保され、それとは別に、SAVE / LOAD のために 1 つ分の領域が常に確保されている。ブロックがすべて使用中になると、それ以上ファイルは開けない。

デバイスルーチンの立場から見れば、重要なのは次の 2 点である。

- ブロックは OPEN の成功時にインタープリタから渡され、CLOSE まで同じアドレスが保たれる。ルーチンは、ブロックのアドレス自体を自分のワークエリアに覚えておく必要はなく、毎回の呼び出しで HL を信じればよい。
- ブロック内の自分用の項目以外は、インタープリタが管理している。勝手に書き換えると、ファイル番号との対応やバッファ管理が壊れる。

# 第6章 実装の指針

## 6.1 ルーチンの骨格

デバイスルーチンは、1 つの入口にすべての呼び出しが集まる形になる。入口での仕事は、A レジスタの値による振り分けだけである。

1. A が FFH なら識別（第3章）。PROCNM を自分のデバイス名と照合し、自分のものでなければ CY = 1 で戻る。自分のものであれば、装置 ID を A に入れて CY = 0 で戻る。
2. A が要求コード（0〜18 の偶数）なら操作（第4章）。FD99H の装置 ID で対象デバイスを判別し、HL の指すブロックを文脈として、要求ごとのハンドラへ振り分ける。振り分けは、要求コードを添字にしたジャンプテーブルで行うのが定石であり、SUB ROM の実装もこの形である（3.5 節）。

## 6.2 骨格コード

次に、規約に基づく骨格を Z80 アセンブラで示す。これは仕様をコードの形に写したものであり、特定の製品のコードではない。デバイス名は "MYDEV"、装置 ID は 0 の 1 デバイスだけを持つ例である。

```
; ROM ヘッダ（4000H 配置）
        db      "AB"
        dw      init            ; INIT
        dw      0               ; STATEMENT（使わない）
        dw      device          ; DEVICE
        dw      0               ; TEXT（使わない）
        ds      6, 0            ; 予約

; デバイスルーチン入口
;   A = FFH: 識別 / A = 0〜18: 要求コード
;   識別時: PROCNM(FD89H) にデバイス名
;   操作時: FD99H に装置 ID、HL = チャンネルポインタ
device:
        inc     a
        jr      z, identify     ; FFH だった → 識別
        ; 操作: A = 要求コード + 1（1, 3, 5, ... 19）
        push    hl              ; チャンネルポインタを退避
        ld      hl, optable - 1
        add     a, l
        ld      l, a
        adc     a, h
        sub     l
        ld      h, a
        ld      a, (hl)
        inc     hl
        ld      h, (hl)
        ld      l, a
        ex      (sp), hl        ; 退避したポインタと行き先を交換する
        ret                     ; ハンドラへ（HL = チャンネルポインタに復元されている）

identify:
        ld      hl, 0FD89h      ; PROCNM
        ld      de, devname
id_loop:
        ld      a, (de)
        cp      (hl)
        jr      nz, id_no       ; 1 文字でも違えば自分のデバイスではない
        inc     hl
        inc     de
        or      a
        jr      nz, id_loop
        ; 一致した。装置 ID = 0 を返して CY = 0
        xor     a               ; A = 0（装置 ID）、CY = 0
        ret
id_no:
        scf                     ; CY = 1 で戻る（次のカートリッジへ）
        ret

devname:
        db      "MYDEV", 0

optable:
        dw      op_open         ; 0: OPEN
        dw      op_close        ; 2: CLOSE
        dw      op_random       ; 4: ランダムアクセス
        dw      op_output       ; 6: シーケンシャル出力
        dw      op_input        ; 8: シーケンシャル入力
        dw      op_loc          ; 10: LOC
        dw      op_lof          ; 12: LOF
        dw      op_eof          ; 14: EOF
        dw      op_fpos         ; 16: FPOS（詳細未確認）
        dw      op_backup       ; 18: バックアップ（詳細未確認）
```

骨格を書くにあたっての注意を 2 点挙げる。

- 操作の振り分けで HL をテーブル引きに使う場合、チャンネルポインタとしての HL は壊れる。骨格では、振り分けの前に HL をスタックへ退避し、行き先と交換してから RET することで、ハンドラへは HL = チャンネルポインタの状態で渡している（実物の SUB ROM の実装も同じ作法である）。
- 識別の照合は、名前の終端（00H）まで一致して初めて成功である。途中まで一致しただけで引き受けると、他人のデバイス名の前方一致を横取りしてしまう。

## 6.3 注意点

- **スタックポインタを壊さない。** ルーチンはインタースロットコールで呼ばれる。SP を含め、戻りの約束を守ること。
- **ルーチンは 4000H〜7FFFH のページに置く。** これは DEVICE フィールドの規則である（2.2 節）。自分のスロットがページ 1 に選択された状態で実行されるので、ページ 1 の中では自分の ROM をそのまま参照できる。逆に、ページ 1 の RAM や他スロットのデータを参照する場合は、スロット切り替えを自前で行う必要がある。
- **ワークエリアは SLTWRK を使う。** スロット×ページごとに 2 バイトのポインタ領域 SLTWRK（FD09H〜）が用意されている。大きなワークエリアは INIT で確保し、そのアドレスを SLTWRK に保存しておくのが MSX の作法である。
- **識別で引き受けたら、操作は必ず完結させる。** OPEN で成功を返した以上、CLOSE までのすべての要求に応答しなければならない。応答できない要求があるなら、識別の段階で引き受けないか、エラーで返すこと。
- Datapack 自身が述べているとおり、デバイスの制御が目的なら、STATEMENT 拡張（CALL 文）で制御する方が現実的な場合も多い。DEVICE 機構が本当に必要になるのは、「BASIC のファイル入出力の文法そのままで、自前の入出力先を使わせたい」ときである。

## 6.4 似て非なる仕組み

混同しやすい近縁の仕組みと、本書の DEVICE 機構との違いを整理する。

|仕組み|何を増やすか|登録の方法|
|-|-|-|
|DEVICE（本書）|BASIC のファイルデバイス（`OPEN "DEV:"`）|ROM ヘッダの DEVICE フィールド|
|STATEMENT 拡張|BASIC の文（`CALL 文`）|ROM ヘッダの STATEMENT フィールド。識別の作法（PROCNM と CY）は DEVICE と同型|
|拡張 BIOS（EXTBIO）|機械語プログラム向けのデバイスドライバ呼び出し|デバイス番号による登録。BASIC のファイル文法とは結び付かない|
|ディスク（A: など）|BASIC のディスクファイル|ディスク ROM が独自の経路でインタープリタとつながる。DEVICE フィールドは使わない（手元のディスク ROM はすべて DEVICE = 0000H であることを確認している）|

特にディスクについては、「デバイスなのだから DEVICE 機構だろう」と考えがちだが、実際は別経路である。本書の機構で増えるのは、あくまでカートリッジ（および SUB ROM のような内蔵 ROM）が提供する名前付きデバイスである。

# 第7章 実働サンプル：ポート入出力デバイス "MSX"

## 7.1 サンプルの構成

第6章の骨格を、実際に動く形にしたサンプルを示す。題材は I/O ポート 10H である。ROM カートリッジにデバイスドライバを載せると、BASIC から次のように書けるようになる。

```
OPEN "MSX:" FOR OUTPUT AS #1
PRINT #1, "1234"
CLOSE #1
```

これで、文字列 "1234" と PRINT 文が付ける CR/LF が、バイト列としてポート 10H へ出力される。入力側も用意してあり、`OPEN "MSX:" FOR INPUT AS #1` とすれば、ポート 10H からバイト列を読み込める。

サンプルは次のファイルで構成され、本書と一緒に配布される。

|ファイル|内容|
|-|-|
|msxport.asm|デバイスドライバ本体。zma（Z80/R800 マクロアセンブラ）記法、4000H 配置|
|msxport.rom|ビルド済みカートリッジ ROM イメージ（16KB）|
|demo.bas|OUTPUT / INPUT のデモプログラム（ASCII 形式）|
|autoexec.bas|デモ用ディスクの AUTOEXEC.BAS（demo.bas を実行する）|
|README.md|ビルド方法と使い方、検証の記録|

## 7.2 動かし方

ビルドは、ソースのあるディレクトリで zma を実行するだけである（zma の引数は相対パスで指定する）。

```
zma msxport.asm msxport.rom
```

"Success." と表示されれば成功で、ソース末尾の SPACE により 16KB にパディングされた ROM イメージが得られる。実機では EPROM 等に焼いてカートリッジ化し、エミュレータではカートリッジスロットに挿す。MSX を普通に起動すれば Disk BASIC がそのまま使え、このカートリッジは自分のデバイス名以外には干渉しない。デモを試すには、720KB の MSX ディスクに autoexec.bas と demo.bas を入れて起動する。

## 7.3 msxport.asm の要点

登録はヘッダの DEVICE フィールドだけである。INIT も STATEMENT も使わない。

```
; カートリッジヘッダ（4000H 配置）
romtop:
        db      "AB"
        dw      0               ; INIT（使わない）
        dw      0               ; STATEMENT（使わない）
        dw      device          ; DEVICE ★ここが登録の本体
        dw      0               ; TEXT（使わない）
        db      0, 0, 0, 0, 0, 0    ; 予約（0 で埋める）

; デバイスルーチン入口
device:
        inc     a
        jr      z, identify     ; FFH だった → 識別
        ; 操作: A = 要求コード + 1。1 エントリ 2 バイトの
        ; テーブルなので optable - 1 + A が目的のエントリを指す
        push    hl              ; チャンネルポインタを退避
        ld      hl, optable - 1
        （中略）
        ex      [sp], hl        ; 行き先と退避したポインタを交換
        ret                     ; ハンドラへ（HL = チャンネルポインタ）

identify:
        ld      hl, PROCNM      ; PROCNM = 0FD89H（識別時の名前）
        ld      de, devname     ; "MSX", 0
        （中略）                ; 終端まで完全一致したら A = 0, CY = 0
                                ; 違えば CY = 1 で素通り
```

本体はポートへの出し入れそのものである。出力は C レジスタの 1 文字をそのままポートへ出す。

```
op_output:                      ; 要求 6: シーケンシャル出力
        ld      a, c
        out     [PORT], a       ; PORT = 10H
        ret
```

入力は、ポートを読むことがそのまま 1 文字の入力になる。ここで、このサンプルの INPUT の意味づけが入る。**FFH を EOF と定義する**のである。何も接続されていないポートを読むと、オープンバスで FFH が返る。したがって未接続のときは「データが無い = EOF」に自然になり、INPUT 側のプログラムはエラーなく安全に終わる。

```
op_input:                       ; 要求 8: シーケンシャル入力
        in      a, [PORT]
        cp      0xFF
        jr      z, inp_eof
        or      a, a            ; CY = 0、A = 受け取った文字
        ret
inp_eof:
        scf                     ; CY = 1（EOF）
        ret
```

対応する要求としない要求の切り分けは、次のとおりである。OPEN は INPUT / OUTPUT / APPEND を引き受け（APPEND はポート相手では OUTPUT と同じ扱い）、RANDOM は Bad file mode（エラー番号 61）を返す。LOC / LOF は、ポートに位置も大きさも無いので常に 0 を返す。FPOS（16）とバックアップ（18）は、4.10 節のとおり詳細が未確認なので未実装とし、呼ばれたら Illegal function call（エラー番号 5）で返す。エラーはどちらも 4.11 節の方法（E にエラー番号、CALBAS 経由で 406FH）で起こす。

## 7.4 demo.bas

デモプログラムは、ユーザーが最初に思い浮かべる使い方そのままである。

```
10 ' MSXPORT DEMO -- DEVICE "MSX:" = I/O PORT 10H
20 PRINT "=== MSXPORT DEMO ==="
30 OPEN "MSX:" FOR OUTPUT AS #1
40 PRINT #1, "1234"
50 CLOSE #1
60 PRINT "OUTPUT: 1234 + CRLF SENT TO PORT 10H"
70 OPEN "MSX:" FOR INPUT AS #1
80 IF EOF(1) THEN PRINT "INPUT: EOF - NOTHING CONNECTED": CLOSE #1: END
90 LINE INPUT #1, A$
100 PRINT "INPUT: RECEIVED: "; A$
110 CLOSE #1
120 END
```

INPUT 側は、まず EOF(1) を見るのが要点である。送信側のハードが付いていてデータが来ていれば EOF ではないので、そのまま LINE INPUT # で 1 行（CR まで）を受けて表示する。何も付いていなければ EOF になり、エラーを出さずに終了する。

## 7.5 検証結果

このサンプルは、エミュレータ（openMSX、FS-A1ST 相当のディスク付きマシン）で実際に動かして検証した。カートリッジとして挿したまま起動し、AUTOEXEC.BAS から demo.bas を走らせている。通常の BASIC 起動とディスクからの読み込みが壊れないことも、この時点で確認できている。

ポート 10H への書き込みは、デバッグ機能の I/O ウォッチポイントで記録した。PRINT #1, "1234" に対して、実際に次のバイト列が出た。

```
49 50 51 52 13 10       ("1" "2" "3" "4" CR LF)
```

デバイスルーチンが受けた要求の列も、トレース用のビルド（入口で A の値を別ポートへ出すだけの差分）で記録した。

|順序|要求|備考|
|-|-|-|
|1|識別（FFH）|OPEN "MSX:" FOR OUTPUT に伴う|
|2|OPEN（0）|モード = OUTPUT|
|3〜8|出力（6）× 6|"1234" と CR/LF が 1 文字ずつ|
|9|CLOSE（2）||
|10|識別（FFH）|OPEN "MSX:" FOR INPUT に伴う|
|11|OPEN（0）|モード = INPUT|
|12|EOF（14）|EOF(1) の評価。ポート読み = FFH で EOF 成立|
|13|CLOSE（2）||

識別は OPEN のたびに呼ばれること、この経路ではランダムアクセス（4）・FPOS（16）・バックアップ（18）が呼ばれないことを確認した。実行画面は次のとおりで、OUTPUT の送信完了と、INPUT が EOF で終わったことが表示されている。

![デモの実行画面](images/msxport_demo.png)

エラー経路も確認した。`OPEN "MSX:" AS #1` のように FOR を省略すると RANDOM モードのオープンになるが（なお `FOR RANDOM` という書き方は MSX-BASIC の文法に無く、Syntax error になる）、このサンプルは Bad file mode で返す。行番号付きで "Bad file mode in 10" と表示され、4.11 節のエラー方法が意図どおり働くことが分かった。

![Bad file mode の表示](images/msxport_err.png)

また、無関係なデバイス名 `OPEN "ZZZ:"` は ERR = 56（Bad file name）となり、この ROM が他人のデバイス名を横取りしない（識別の素通りが正しい）ことも確認した。

## 7.6 INPUT の意味づけと実機での注意

INPUT の意味づけを、このサンプルの定義として改めて整理する。

- CR（0DH）を行の終端とする。LINE INPUT # / INPUT # は CR までを 1 行として読む。
- FFH を EOF とする。未接続 = オープンバスの FFH が、そのまま EOF になる。
- テキスト行専用であり、FFH のデータそのものは受け取れない。

検証範囲の線引きも正直に書いておく。エミュレータで確認したのは、未接続（FFH）を EOF として安全に終わる経路までである。**送信側のハードを実際に付けてのバイト受信は、エミュレータでは再現できないため実機確認待ち**であり、コードと本書の作法（4.7 節の入力規約）の整合で担保している。

もう 1 つ、実ハードに付けるときの注意がある。このサンプルの EOF ハンドラは、判定のためにポートをのぞく（読む）。読み出しに消費の副作用がない単純なポートなら問題ないが、読むたびにデータが進む FIFO 型のハードでは、EOF 判定の読みがデータを取りこぼす。実ハードに合わせて、EOF 判定と入力で読みを共有する設計（読み済みの 1 文字をチャンネルブロックに保持する）に変えること。

## A.2 ROM 調査の結果

本書の執筆にあたり、手元の ROM イメージ（エミュレータ用システム ROM 群と、提供を受けたファームウェア類）を走査し、ヘッダの DEVICE フィールドが 0 以外のものを探した。結果は次のとおりである。

- カートリッジ型ヘッダ（ID「AB」）を持つイメージ——ディスク ROM 各種、漢字ドライバ、FM-BASIC、MSX-Write II、MSX-DOS2 カートリッジなど——は、**すべて DEVICE = 0000H** であった。ディスクが DEVICE 機構を使わないことの、実物での確認である。
- ゲーム ROM 1 件で非ゼロの値が見えたが、ヘッダ位置に置かれた文字列データの断片であり、デバイスの実装ではない（誤検出）。
- **SUB ROM（ID「CD」）には実装があった**。MSX2+ 系の SUB ROM（FS-A1ST / FS-A1GT / FS-A1WSX / HB-F1XDJ）は、DEVICE フィールドにメモリディスク用のルーチン（36B4H または 3658H）を持ち、その入口の構造——A = FFH の判定、PROCNM とデバイス名 "MEM0" の照合、キャリーフラグによる応答、要求 0〜18 に対応する 10 本のジャンプテーブル——が、Datapack の記述と一致することを確認した。本文 3.5 節の記述はこの観察に基づく。なお、ROM のコードやデータそのものは本書に含めていない（構造と振る舞いの記述に限っている）。

RS-232C カートリッジのような、カートリッジ型 DEVICE の代表的な製品については、手元に実物がなく、本書では構造の検証対象にできなかった。

## A.3 未確認事項の一覧

次の事項は、入手できる資料と実物では裏が取れなかったため、本文では未確認として切り分けた。

|事項|状況|
|-|-|
