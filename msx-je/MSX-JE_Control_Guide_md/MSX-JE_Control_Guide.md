# 第1章 概要

## 1.1 MSX-JE とは何か

MSX-JE は、MSX 標準の日本語入力フロントエンドプロセッサ（FEP）の規格である。規格ができる以前は、ワープロソフトなどがそれぞれ独自の日本語入力処理を内蔵していた。そのため、別のソフトで日本語を入力しようとすると、そのソフトごとに使い方の違う入力処理を覚え直す必要があった。MSX-JE は、日本語入力の機能と、それをプログラムから呼び出す方法とを標準化したものである。内蔵の S-RAM 辞書に登録した単語が、漢字 BASIC からでも他のソフトからでも共通に使える、といったことがこの規格の狙いである。

MSX-JE の実体は、本体内蔵の ROM やカートリッジとして提供されるモジュールである。代表的な実装には、松下 FS-A1ST などに内蔵されたもの、ソニー HB-F1XDJ のもの（Halnote 系）、アスキーの VJE-80 / VJE-80A、MSX-Write / MSX-Write II に内蔵されたものなどがある。アプリケーション（以下 AP）は、拡張 BIOS（EXTBIO）経由でモジュールを発見し、インタースロットコールでその機能を呼び出す。呼び出しの基盤は全実装で共通であり、第2章で述べる。

本書は、MSX-JE をプログラムから制御するための実践的な手引きである。公式資料である MSX-Datapack Vol.2 第7章§5 の記述は、関数の一覧としては揃っているものの、実際に動くプログラムを書くには情報が不足している箇所がある。本書では、MSX-DOS2 上で動作するテキストエディタ MSX-NOTE の開発を通じて、実際の JE モジュールで測定した振る舞いを基に、「この手順で呼べば動く」という形に整理した。

## 1.2 2つのインターフェイス

MSX-JE には、性質の異なる 2 つのインターフェイスがある。どちらを使うかは、AP が何をしたいかで決まる。

|項目|仮想端末インターフェイス（VT）|辞書インターフェイス（DIC）|
|-|-|-|
|考え方|変換の UI ロジックは JE 側が持つ|変換の各段階を AP が関数単位で操作する|
|キーの解釈|JE がキューから直接読んで解釈する（AP は変更不可）|全て AP が解釈し、操作を関数呼び出しに割り当てる|
|表示|JE が STB（画面イメージ文字列）を返し、AP が描く|AP が文節構造を持ち、全て自前で描く|
|文節構造|意味データとしては得られない（STB の属性・反転から描画レベルで推測するのみ）|文節ごとに読み範囲・候補一覧・選択中候補を AP が保持できる|
|キーアサインの自由度|実装ごとに固定（振り分けだけが AP の仕事）|自由（ATOK 風の割り当ても可能）|
|実装の負担|小さい（表示だけ）|大きい（読み管理・状態機械・候補 UI・学習への配慮を全て AP が持つ）|
|関数番号|1〜10（共通部 1〜3 を含む）|1〜3（共通）＋ 40h〜50h|

VT は「手早く JE 標準の変換体験を得る」ための道である。変換キーや確定キーの解釈は JE 実装に委ねられ、AP は返ってくる STB を画面に描くだけでよい。漢字 BASIC の漢字入力がこの方式であり、最下行にウィンドウが開いて変換が行われる、あの表示が VT の姿である。

DIC は、カーソル位置に未確定文字列を埋め込むインライン表示（Windows の IME のような表示）や、ATOK 風のキーアサインを実現するための道である。文節の区切り・注目文節を「意味として」持てるのは DIC だけであり、その代償として、読みバッファの管理から候補ウィンドウの描画まで、変換 UI の全てを AP が実装することになる。

なお、どちらのインターフェイスでも、モジュールの発見（第2章）と、Inquiry / Invoke / Release という共通のライフサイクルは同じである。関数番号 1〜3 は両インターフェイスで共通に使う。

## 1.3 インターフェース選択は変換結果にも影響する

インターフェースの違いは、API の形だけの話ではない。同じモジュールに同じ読みを渡しても、経路によって変換結果が変わることが、実測で確認されている。

FS-A1ST 内蔵 JE に対し、読み「かんじ」を変換したときの第一候補は次のとおりだった。

|経路|第一候補|
|-|-|
|DIC の henkan（MSX-NOTE の変換）|寛治|
|漢字ドライバ経路（BASIC の `CALL KANJI` での変換）|感じ|

どちらも同じ A1ST モジュールの辞書を使っている。それでも結果が違うのは、変換の組み立て方が経路ごとに異なるためである。DIC では AP が読みを文節に組み立てながら変換を進めるのに対し、漢字ドライバ側の変換はドライバ内部の手順で読み全体を処理する。候補の学習状態によっても第一候補は変わり得るが、「インターフェースを選ぶことは、変換の振る舞いを選ぶことでもある」という点は押さえておきたい。

## 1.4 本書の立場と実測について

本書の記述は、次の優先順位で裏付けを取っている。

1. 実際の JE モジュールでの実測（fork openMSX および BlueMSX+ 上の実ファームウェア、ならびに実機での動作報告）
2. MSX-Datapack Vol.2 第7章§5 の記述
3. MSXテクニカルガイドブック第四版 第５部（VJE-80A 仕様書を参考に編まれた資料）

Datapack の記述と実測が食い違う箇所では、実測を正とし、その旨を注記した。代表的な例を挙げる。

|事項|資料の記述|実測|
|-|-|-|
|han_hira の機能番号|一部の記述で 45h とされることがある|43h が正しい（45h は hira_kata）。A1ST / Sony の両方で確認|
|kakutei2 の前提|ji_koho は必ずしも必要でない|FS-A1ST では、列挙を経ない kakutei2 は消費長 0 を返した。常に列挙してから呼ぶこと（3.7 節）|
|henkan の戻り値 A|先頭文節の候補数|候補数とは解釈できない値（45h や 52h など）が返ることがある。「0 か否か」だけを使うこと（3.6 節）|

逆に、実測できていない事項は、その旨を明記して推測で埋めていない。特に MSX-Write の JE モジュール単体の DIC 挙動は、検証環境の制約で測定できておらず、「実測不能・実機での確認待ち」として第4章に切り分けた。

本書で検証に使った主な環境は次のとおりである。

|対象|環境|
|-|-|
|Panasonic 内蔵 JE|FS-A1ST 実ファームウェア、fork openMSX / BlueMSX+|
|Sony JE|HB-F1XDJ 実ファームウェア（Halnote）、fork openMSX|
|MSX-Write JE|実機（SX-2 ＋ MSX-Write カートリッジ）での MSX-NOTE 動作報告。単体測定は未実施|
|クライアント実装|MSX-NOTE（MSX-DOS2 用テキストエディタ）、JE スパイクプログラム、KID.COM（解析対象）|

本書では、JE モジュールの ROM の内容そのもの（コードや辞書データ）は扱わない。記述はインターフェースと振る舞いに限る。

# 第2章 検出とライフサイクル

MSX-JE を使うプログラムは、どのインターフェイスを使う場合でも、まず「モジュールを見つける → ワークエリアを確保して起動する → 使い終わったら解放する」という共通の手順を踏む。本章はその手順を、実測で確認した形で述べる。

## 2.1 拡張 BIOS の確認

最初に、拡張 BIOS（EXTBIO）そのものが使えるかを確認する。

- ワークエリア HOKVLD（FB20h）の bit0 が 1 であれば、拡張 BIOS が存在する。0 なら拡張 BIOS 自体が無く、MSX-JE も存在しない。
- 補助的な確認として、EXTBIO のエントリ（FFCAh）のバイトが C9h（RET）でないことも見る資料がある。HOKVLD の確認が主で、こちらは併用してよい。

## 2.2 モジュールテーブルの取得

EXTBIO を、デバイス番号 16（MSX-JE）、機能番号 0 で呼ぶと、接続されている JE モジュールの一覧が返る。

|レジスタ|設定|
|-|-|
|A|（EXTBIO の規約に従う）|
|D|16（MSX-JE のデバイス番号）|
|E|0（機能番号：情報取得）|
|B|RETURN 情報エリアのある RAM のスロットアドレス（ページ 3 の RAM スロット。F344h の値）|
|HL|RETURN 情報エリアの先頭アドレス|

呼び出しに先立ち、RETURN 情報エリア（64 バイト）はゼロクリアしておくこと。戻り時、HL はモジュール 1 台につき 4 バイト進む。HL が呼び出し前と変わらなければ、JE モジュールは存在しない。複数台が接続されていること（内蔵 JE とカートリッジ JE の併存など）があり得るので、テーブルは台数分だけ並ぶものとして扱う。

各エントリは 4 バイトで、次の形をしている。

|オフセット|サイズ|内容|
|-|-|-|
|+0|1 バイト|ケーパビリティベクトル|
|+1|1 バイト|スロットアドレス|
|+2|2 バイト|エントリアドレス（リトルエンディアン）|

実測例を示す。FS-A1ST の DOS2 環境では、先頭エントリは `F0 8F 28 40`、すなわちケーパビリティ F0h、スロット 8Fh（拡張スロット 3-3）、エントリ 4028h だった。HB-F1XDJ では `F0 8C 90 60`（スロット 8Ch、エントリ 6090h）、MSX-Write II を併存させた構成では 2 番目のエントリとして `F0 01 28 40`（スロット 01h、エントリ 4028h）が得られた。

## 2.3 ケーパビリティベクトル

ケーパビリティベクトルは、モジュールの持つ機能を示すビット列である。ビットの意味は「0 で利用可能」という負論理になっている点に注意する。

|ビット|7|6|5|4|3|2|1|0|
|-|-|-|-|-|-|-|-|-|
|意味|1（拡張用）|1（拡張用）|1（拡張用）|1（拡張用）|辞書登録・削除|辞書 I/F|仮想端末 I/F|共通部|

- bit0 = 0: MSX-JE 互換の共通部がある（両インターフェイスの前提）
- bit1 = 0: 仮想端末インターフェイスがある
- bit2 = 0: 辞書インターフェイスがある
- bit3 = 0: 辞書登録・削除（4Fh / 50h）が使える
- bit4〜7: 拡張用で、現在の実装ではすべて 1

判定はマスクで行う。VT だけを使うなら `cap AND 03h == 0`、DIC だけなら `cap AND 05h == 0`、両方なら `cap AND 07h == 0` を確認する。特定の値との一致で判定してはいけない。例えば VJE-80 のケーパビリティは F8h だが、これは「登録・削除なし」を含んだ値であり、F8h との比較で JE の有無を判定するコードは他のモジュールで誤動作する。

実在の値の例： VJE-80 = F8h、VJE-80A = F0h、FS-A1ST 内蔵 = F0h、HB-F1XDJ = F0h、MSX-Write II = F0h（いずれも実測または資料値）。

## 2.4 呼び出し規約と RST 30h スタブ

モジュールへの呼び出しは、テーブルのスロットアドレスとエントリアドレスを使ったインタースロットコール（RST 30h）で行う。

- A = 関数番号
- HL = ワークエリア先頭アドレス（Inquiry を除き必須）
- BC / DE = 関数ごとのパラメータ
- 戻り値レジスタと SP 以外のレジスタは保存されないものとして扱う
- ワークエリアと、間接参照されるパラメータ（文字列バッファ等）は、ページ 2 か 3 に置き、そのページをイネーブルしてから呼ぶ。EXTBIO を呼ぶ時点では、スタックもページ 3 にあることが必要である

呼び出しスタブは、スロットとエントリをテーブルから書き込む形にするのが定石である（書籍のリストもこの形を取る）。

```
; JE 呼び出しスタブ
; in:  A = 関数番号, BC / DE = パラメータ
; out: 各関数の戻り値（HL にはワークエリアが自動で入る）
call_je:
        ld      hl, JE_WORK     ; ワークエリア
        rst     0x30
je_slot:
        db      0               ; テーブルから転記したスロット
je_entry:
        dw      0               ; テーブルから転記したエントリ
        ret
```

この形のスタブは、MSX-NOTE の開発に先立つスパイクプログラムで実動作を確認したものである。第6章の実装例でも同じスタブを使う。

## 2.5 Inquiry とワークエリア

関数 1（Inquiry）は、モジュールが必要とするワークエリアの大きさを返す。

|戻り値|意味|
|-|-|
|HL|MAX: ワークエリアの最大値。これ以上渡してもモジュールは使わない|
|DE|MIN: 最低限必要な大きさ|
|BC|MIN2: 学習機能を使う場合に最低限必要な大きさ|

実測値と資料値を並べる。

|実装|MIN|MIN2|MAX|出典|
|-|-|-|-|-|
|Panasonic 内蔵（FS-A1ST）|512|520|512|実測|
|Sony（HB-F1XDJ）|2,560|2,560|2,560|実測|
|VJE-80|2,304|3,328|3,328|資料|
|VJE-80A|512|520|520|資料|

FS-A1ST の MAX（512）が MIN2（520）を下回るような、一見奇妙な値が返ることもある。実務上の結論は単純で、**常に 2,560 バイトを確保すればよい**。MSX-JE の仕様上、必要なワークエリアが 2,560 バイトを超えることはないとされており、2,560 バイトを常時確保する設計なら Inquiry 自体を省略できる。学習機能を使う場合は MIN2 以上が必要なことにだけ注意する。

なお、ワークエリアは TPA 内の自前の領域（プログラムの BSS 等）に取ること。スパイクでは固定アドレスに直置きして TPA 上限を跨ぐ配置になったが、実プロダクトでは自プログラムの確保領域内に置くべきである。また KID.COM は、Inquiry の MIN2 に自前のコンテキスト分（5Eh バイト）を加えた大きさを TPA 上限の直下に確保していた（5.6 節）。確保の仕方には幅があるが、「MIN2 以上、最大 2,560 バイト」という枠は共通である。

## 2.6 Invoke と Release

関数 2（Invoke）でモジュールの使用を開始し、関数 3（Release）で終了する。

|関数|入力|備考|
|-|-|-|
|2 Invoke|HL = ワークエリア、DE = ワークエリアの大きさ|使用開始時に必ず呼ぶ|
|3 Release|HL = ワークエリア|プログラム終了時に必ず呼ぶ|

Release は省略できない。Datapack は、Release を呼ばずに電源を切ると学習辞書（SRAM）が壊れることがあると明記している。学習内容はモジュール側の SRAM に保存されるため、Invoke したモジュールは、異常終了の経路を含め、必ず Release まで到達するようにプログラムを設計すること（2.8 節）。

なお Invoke は「使用開始時に 1 回」が原則である。変換のたびに Invoke / Release を繰り返す設計はしない。MSX-NOTE でも、Invoke は起動時に 1 回だけ行い、Release は終了処理でのみ呼んでいる。

## 2.7 モジュールの選択

モジュールが複数台ある場合、どれを使うかは AP の方針で決める。実在の実装は 2 通りの方針を取っている。

|実装|選択方針|
|-|-|
|MSX-NOTE（およびスパイク）|先頭のエントリを採用し、ケーパビリティで使うインターフェイスの有無を判定する|
|KID.COM|エントリを走査し、`(cap AND 7) == 0`（共通部・VT・DIC のすべてがある）を満たす最初のエントリを採用する|

資料（ガイドブック）には、複数台ある場合はメニューを出してユーザーに選ばせるのが望ましい、という指針もある。ただし機種によっては内蔵 JE が必ず先に立ち上がり、外付け JE を使えない場合があることも知られている（松下 FS-4600F に MSX-WRITE を差した場合の例が知られている）。

どちらの方針を取るにせよ、判定はケーパビリティのマスクで行い、特定値との比較は避けること（2.3 節）。また、二重 JE 構成にはエミュレータ環境特有の観測もあるため、4.6 節も参照してほしい。

## 2.8 終了経路の設計

Release の保証は、プログラムの終了経路の設計で決まる。MSX-NOTE で採用し、実動作を確認した形は次のとおりである。

1. 要件検査（DOS2、マッパー、漢字 ROM、VDP 等）と、コマンドラインのファイル読み込みエラーなど「JE を使わずに終わる」経路は、すべて Invoke より前に済ませる。Invoke 前の終了では Release は不要である。
2. Invoke は、メインループに入る直前に 1 回だけ呼ぶ。
3. Release は、単一の終了処理（cleanup）の先頭でのみ呼ぶ。Invoke 後に起こる全ての失敗経路（ファイル読み込みエラー等）は、エラー表示の後に必ず cleanup へ合流させる。
4. Release を呼んだかどうかは「Invoke 済み」フラグで管理し、二重呼び出しを避ける。

あわせて、JE の使用開始時には入力キューのドレイン（残留キーの破棄）を入れておくとよい。スパイクの実験では、前セッションの残留キーが変換開始直後に流れ込み、空の確定が発生する事象を観測した。

# 第3章 辞書インターフェイス詳説

辞書インターフェイス（DIC）は、変換の各段階を AP が関数単位で操作するインターフェイスである。本章では、共通部（関数 1〜3、第2章）に続く 40h〜50h の関数群を、実測で確認した意味論とともに述べる。

## 3.1 テキスト形式

DIC で受け渡す文字列は、すべて次の長さ付き形式である。

|要素|内容|
|-|-|
|先頭 1 バイト|文字数（バイト数。最大 64）|
|続くバイト列|Shift-JIS コード列（全角文字は 2 バイトで数える）|

バッファへのポインタは、関数ごとに BC または DE で渡す。HL は常時ワークエリアの先頭アドレスである（2.4 節）。半角の濁点・半濁点は 1 文字として数える。半角では使えない文字（「ヰ」「ヱ」「ヴ」「ヵ」「ヶ」の半角形など）があることにも注意する。

## 3.3 文字種変換（40h〜45h）と部分変換の意味論

40h〜43h の変換関数には、共通の「部分変換」の意味論がある。

- 戻り値 A = 0 なら全て変換できた。
- A ≠ 0 なら、A は「変換できなかった文字の、バッファ上での位置（1 始まり）」である。
- 変換に失敗した場合でも、**変換できた部分はデスティネーションに入っている**（長さ付き形式で）。

この意味論があるため、ローマ字入力の増分変換（3.5 節）のような使い方ができる。44h / 45h（kata_hira / hira_kata）は全角同士の変換で、変換できない文字はそのまま写され、位置を返す動作はしない。

各関数の入力の性格も重要である。han_kata（42h）と han_hira（43h）の入力は「半角文字列」、すなわち半角カナまたはローマ字である。**全角ひらがなを han_kata に渡しても変換できない**（位置 1 で失敗し、結果の長さは 0 になる）。この取り違えは実際に踏んだ罠であり、3.9 節で述べる。

## 3.4 han_hira の意味論

han_hira（43h）は、ローマ字（または半角カナ）の入力を全角ひらがなに変換する。読み入力の土台になる関数であり、その意味論は実測で詳しく確認した。規則は次のとおりである。

- A は「最初の未変換バイトの位置（1 始まり）」。A = 0 は全バイト変換済みを意味する。
- 変換できた部分は dest に残る。dest の内容は、「変換できた最長の接頭辞」を入力したときの結果と一致する（接頭辞分割性）。
- 失敗位置は音節単位で決まる。例えば "ky" は A = 1 で dest は空（"k" だけでも "ky" だけでも音節を成さない）。
- "n" 単独は変換されない（A = 1、dest 空）。"nn" と重ねて初めて「ん」になる。
- 末尾の子音が「次の音節の予告」として働く場合がある。"kanp" は「かん」まで変換され A = 4（'p' が未変換）だが、'p' の存在によって直前の 'n' が「ん」に変換されている。末尾が 'n' の場合は、その 'n' 自体が「ん」の源として消費される（"kann" は A = 0 で「かん」）。

実測表の抜粋を示す（全 27 件は付録 A.3。A1ST と Sony で共通する入力はすべてバイト一致した）。

|入力|A|dest|読み取れる規則|
|-|-|-|-|
|n|1|（空）|単独の n は変換されない|
|nn|0|ん|nn で ん になる|
|nnn|3|ん|3 つ目の n が未変換として残る|
|on|2|お|末尾 n は未変換（位置 2）|
|onna|0|おんあ|文中の nn は ん に変換される|
|kan|3|か|末尾 n が未変換位置|
|kana|0|かな|—|
|kanji|0|かんじ|—|
|ky|1|（空）|音節を成さず全体が未変換|
|kak|3|か|末尾 k が未変換位置|
|kanp|4|かん|子音 p の予告で n が ん に変換される|
|kann|0|かん|末尾 n は ん の源として消費される|

ただし、この A の解釈をそのまま表示に使うことには注意が要る。実装によっては A の意味論が仕様どおりでない可能性があり、NOTE では A に依存しない導出方式（4.2 節）を採用した。本節の意味論は「仕様どおりの実装（A1ST / Sony）ではこうなる」という実測記録として読んでほしい。

## 3.5 ローマ字入力の増分変換

ローマ字で読みを入力する場合の、実証済みの方式は次のとおりである。

1. 打鍵ごとに、保留中のローマ字文字列**全体**へ han_hira をかけ直す。
2. 表示は「変換済みのかな ＋ 未変換のローマ字末尾」とする。未変換末尾は、変換結果に現れなかった末尾部分であり、半角ローマ字のまま表示する。
3. 確定したかなの部分は読みとして蓄積し、ローマ字側は未変換分だけを保持し直す、という形でもよい（NOTE は読み全体を保持し、毎回かけ直す方式）。

部分変換の意味論（3.3 節）があるため、この方式で「か」の後に 'n' が 1 つ付いた段階では末尾に "n" が見え、もう 1 つ 'n' が付くと「ん」に変わる、という自然な増分表示が得られる。

なお、キーがかな文字として届く場合（KANA ロック等による直接入力）は、ローマ字変換を経ず、そのまま読みに加える。

## 3.6 henkan と候補列挙

henkan（47h）は、読み全体に対する連文節変換を開始する。入力は DE = 読みデータ（長さ付き形式の全角かな文字列）である。資料の例は片仮名読みで書かれているが、実測では平仮名読みでも変換できた（A1ST / Sony）。

戻り値 A については注意が要る。資料は「先頭文節の候補数」とするが、実測では候補数とは解釈できない値（45h や 52h など）が返ることがあった。**A は「0 か否か」だけを使う**こと。0 なら候補なし、それ以外なら変換が開始できた、と解釈する。

変換開始後の候補取得は ji_koho（48h）で行う。

- DE = 候補バッファ、BC = 後続文節バッファを渡す。
- 戻り値 A は、候補ブロック内での候補の通し番号。**A = 0 で候補なし＝列挙の終端**であり、巻き戻りはしない。
- 候補バッファには先頭文節の候補が、後続文節バッファには「残りの全てを第一候補で変換した文字列」が入る。この後続文字列はプレビューとして使えるが、文節構造を AP が持つ設計では使わなくてよい（NOTE は不使用）。
- zen_koho（49h）は候補を 1 つ戻す。

実測例： 読み「かんじ」に対する ji_koho の列挙は、寛治 → 感じ → 感じ → 漢字 → 幹事 → 監事 の 6 件で、7 回目の呼び出しが A = 0 を返して終わった。候補の内容と順序は学習状態で変わる（2.6 節、第4章 4.5 節）。検証コードは「特定の候補が含まれるか」「表示と確定結果が一致するか」で判定し、候補の固定値を前提にしてはいけない。

候補が多い場合のために、候補は「ブロック」（優先度の異なる候補群）に分かれている。ji_block（4Ah）/ zen_block（4Bh）でブロックを移動し、A には新しいブロックの候補数が返る（0 でブロックなし）。ブロック移動は周回する実装がある。NOTE ではブロックを使わず、最初のブロックの列挙のみで最大 40 件までを対象とした。

## 3.7 kakutei2 による文節構築

文節構造を AP 側に構築する正道は、kakutei2（4Dh）を使った「消費して進める（consume-and-shift）」反復である。

- kakutei1（4Ch）: 先頭文節に E で指定した候補を採用し、**文全体**を変換して結果バッファに返す。
- kakutei2（4Dh）: **先頭文節のみ**を確定する。結果バッファにその文節の変換結果が入り、A には「確定した文節が消費した読みの長さ（バイト数）」が返る。

文節配列の構築手順は次のとおりである。

1. 読み全体に henkan をかける。
2. ji_koho の列挙で先頭文節の候補一覧を得て、選択中の候補まで列挙を進めて同期させる。
3. kakutei2（選択中の候補）を呼び、確定文字列と消費長を得る。
4. 読みポインタを消費長だけ進め、残りの読みに henkan をかけ直して次の文節を作る。
5. 読みが尽きるまで 2〜4 を繰り返す。

実測で確認した構築例（候補 #1 を選んだ場合）： 「やまのうえのいえ」→ [山野][植えのいえ]、「わたしはがくせいです」→ [私は][学生です]、「かんじ」→ [寛治]（1 文節）。各文節について AP は {読みの開始・長さ、候補一覧、選択中候補、変換後文字列} を保持でき、これがインライン表示（注目文節の反転、下線による区切り）の土台になる。

**実測上の注意**: kakutei2 の消費長は、ji_koho を先に呼んで列挙を同期させた場合にのみ有効だった。列挙を経ずに kakutei2 を呼ぶと、FS-A1ST では A = 0 が返った。Datapack とガイドブックはいずれも「ji_koho などは必ずしも必要ではありません」と書くが、実測はこれと食い違う。**実装では常に列挙してから kakutei2 を呼ぶこと**。なお kakutei1 / kakutei2 の E は、候補ブロック内での通し番号である。

全文を確定する場面でも、NOTE は kakutei1 の一括確定を使わず、文節ごとに上記の手順で kakutei2 を繰り返して確定文字列を組み立てる。各文節の選択中候補（および 3.9 節の上書きテキスト）を尊重するためである。

## 3.8 文節の伸縮

文節を伸ばす・縮める専用の関数は、DIC には無い。実現方法は、注目文節の読み範囲を ±1 文字変えて、その範囲で henkan し直すことである。

この方式では、伸縮した文節より後ろの連文節としての文脈は切れるため、変換品質は下がり得る。ただし ATOK のような既存の FEP でも文節区切りの変更は再変換を伴う操作であり、実用上の違和感は小さい。NOTE では Shift+← / Shift+→ に文節の縮め／伸ばしを割り当て、再分割のたびに文節を作り直す方式で実動作を確認した。

## 3.9 文字種変換キー（F6〜F10）の実装例

変換中の文節に対する文字種変換は、40h〜45h の変換関数で実現できる。NOTE で作者裁定を経て正式採用した割り当てを示す。

|キー|動作|使う関数と対象|
|-|-|-|
|F6|ひらがな変換|読みを kata_hira（44h）。ローマ字の残渣は han_hira（43h）|
|F7|カタカナ変換|読みを hira_kata（45h）**単独**|
|F8|半角変換|表示文字列を zen_han（41h）|
|F9|全角英数変換|読みを han_zen（40h）|
|F10|半角英数変換|表示文字列を zen_han（41h）|

変換結果は、候補選択とは別の「上書きテキスト」として文節に保持し、読み自体は変えない。確定時は上書きテキストをそのまま使う。

F7 には実際に踏んだ罠がある。当初 F7 を han_kata（42h）→ hira_kata（45h）の連鎖で実装したところ、変換中の組成が消える不具合になった。原因は 3.3 節のとおりで、han_kata の入力はローマ字・半角カナ専用であり、全角ひらがなの読みを渡すと位置 1 で変換不能となり、長さ 0 の結果が返っていたためである。全角ひらがなのカタカナ化は hira_kata（45h）単独が正しい。スパイク段階の記録に「han_kata でカンジ化できた」とあったのも、実際には入力がローマ字だったためであり、関数の対象を取り違えないことが肝要である。

## 3.10 登録と削除（4Fh / 50h）

touroku（4Fh）はユーザー辞書への単語登録、sakujo（50h）は削除である。ケーパビリティの bit3 = 0 のモジュールでのみ使える（2.3 節）。

- 入力: DE = 読みバッファ（長さ付き形式。全角カタカナ、2〜64 バイト）、BC = 単語バッファ（長さ付き形式の単語データ 2〜64 バイトの後に、品詞コード 1 バイトを続けたもの）。
- 品詞コード: 1 = 名詞、2 = 人名（姓）、3 = 人名（名）、4 = 地名、5 = サ変動詞。
- touroku の戻り値 A: 0 = 登録できた、1 = 空き領域がない、2 = 同音語が多すぎる、4 = 読みデータが不適切、8 = 単語データが不適切、16 = 品詞が不適切。機能をサポートしない JE では FFh が返る。
- sakujo の戻り値 A: 0 = 削除できた、1 = 削除すべき単語が見つからない、4 / 8 / 16 は touroku と同じ。未サポートでは FFh。

NOTE は登録・削除の UI を持たないため、本節は資料（ガイドブック）に基づく記述であり、実測はしていない。

## 3.11 設計値の例（MSX-NOTE）

DIC クライアントの設計値として、NOTE で採用し実動作を確認した値を挙げる。

|項目|値|理由|

# 第4章 実装差と落とし穴

MSX-JE は規格だが、実装は複数あり、細部の振る舞いは実装ごとに異なる。本章では、実測で遭遇した実装差と落とし穴を、原因の確定度合いを明示しながら述べる。本章の内容は、特定の実装を非難するためのものではなく、実装差に強いクライアントを書くための記録である。

## 4.1 返値 A の解釈は実装で揺れる前提で設計する

han_hira の返値 A（最初の未変換位置、3.4 節）は、A1ST と Sony の両実装では仕様どおりであることを実測した。しかし NOTE の実機運用では、次のような経緯があった。

- 実機（MSX-Write の JE）で、入力中のローマ字末尾が表示されない問題が報告された。当初の設計は A を信頼して末尾を決めていたため、A の解釈差が原因の候補になった。
- その後の切り分けで、この問題には NOTE 側の描画処理のバグ（末尾の追加処理でレジスタを破壊し、末尾が画面に届いていなかった）という、JE とは無関係の別原因も存在したことが判明した。
- 結局、Write JE の A が仕様と違うかどうかは切り分けられていない（4.7 節）。

教訓は「A が信用できない」ということではない。**「返値の解釈に依存する設計は、実装差があると壊れる」**ということである。次節の導出方式は、A の意味論がどちらの場合でも正しく動くため、堅牢性の観点から推奨する。

## 4.2 je_find_split: 入出力だけから未変換末尾を導く

NOTE で採用した方式（je_find_split）は、han_hira の**入力と出力だけ**から未変換末尾の開始位置を導く。返値 A は一切使わない。

前提として、han_hira には「変換結果は、変換できた最長接頭辞に対する結果と一致する」という接頭辞分割性がある（3.4 節）。また未変換のローマ字末尾は、性質上、数文字以内に収まる。導出は次の手順である。

1. F = han_hira（読み全体）とする。F が空なら、読み全体が未変換末尾である。
2. 接頭辞の長さ s を、読みの末尾から最大 6 文字の範囲で探し、han_hira（rom[0..s]）== F となる最小の s を分割点とする。末尾は s より後ろである。
3. どの s でも一致しない場合に残る曖昧さは、撥音のルックアヘッド（3.4 節の "kanp" 型）だけである。末尾文字が 'n' 以外の子音で、その直前が 'n' で、かつ han_hira（rom[0..len−1]）＋「ん」== F であれば、末尾は最後の 1 文字だけとする。
4. 末尾が 'n' の場合は、その 'n' は「ん」の源として消費されたものとみなし、末尾にはしない。

検証結果は次のとおりである。

|対象|件数|結果|
|-|-|-|
|Sony JE の実測入出力（付録 A.3 の全件）|27 件|導出した分割が JE 自身の A と全件一致|
|A1ST JE の実測入出力|18 件|同上、全件一致|

仕様どおりの実装では導出は A と一致し、A の解釈が異なる実装でも入出力の観測可能な事実だけから決まるため壊れない。プローブ用の余分な han_hira 呼び出しが数回増えるが、読みの再表示は打鍵ごとの処理であり、実用上の問題にはならなかった。

## 4.3 A1ST JE のバッファステージング問題

### 症状

MSX-NOTE を 2 回連続で起動すると、2 回目のセッションで DIC 変換が文字化けした。han_hira が A = 0・出力なしを返し、後段の文節構築が残留 RAM のバイト列を拾うため、「寛治」（8A B0 8E A1）であるべき確定結果が `18 E3 CD CB` のようなコード片（セッション間に読み込まれた COMMAND2.COM の transient コードそのもの）になった。

再現条件は限定的で、NOTE → NOTE の連続セッションでのみ発生した。スパイク単独の連続実行、スパイク → NOTE、NOTE → スパイクでは発生しない。fork openMSX と BlueMSX+ の両方で、工場出荷状態の SRAM からでも再現したため、片方のエミュレータ固有の問題ではないと判断した。

### 原因（実測で確定した範囲）

A1ST JE の DIC 実装は、ページ 0 / 2 にある呼び出し側バッファを、バイト単位の WRSLT コピー（モジュール内のヘルパー）で内部バッファへ転送（ステージング）する。2 回目のセッションでは、このコピーが **0 バイトしか転送しない**。コピー直後にブレークポイントで確認すると、内部バッファは消去状態（FFh）のままだった。han_hira は空の入力を「変換」して返るため、呼び出し側には A = 0・出力なしが返る。

失敗時と健全時で機械状態を比較すると、異なるのはモジュールの SRAM ワークエリア内にある辞書検索数（0A028h）だけだった（健全時 FFFFh、異常時 03E9h）。Invoke の辞書オープン処理は、（0A9EAh）の値を（0A028h）へコピーするが、それは（0A9EAh）を辞書テーブルから再計算する**前**に行われる。初回セッションは消去状態の番兵値 FFFFh を、2 回目以降は前セッションの値をコピーする、という古い値の読み（stale read）である。

なお、その古い値が転送経路のどこをどう塞ぐのか、最終段の因果は命令レベルまで追跡できていない。ここまでの連鎖（ステージングが 0 バイトであること、状態差が（0A028h）のみであること）は実測で確定しているが、最後の一段は未確定としておく。

試して効果がなかった回避策も記録しておく。Release の省略、Invoke 直後の Clear（関数 4）の追加、起動時のダミー変換サイクル（henkan → ji_koho → kakutei2）はいずれも直らなかった。スロット操作で辞書の状態を反転させる方法は、DOS2 のインタースロット管理を壊すため不採用とした。

## 4.4 回避策: DIC バッファはページ 3 に置く

有効だった回避策は、モジュールと受け渡す DIC バッファをページ 2 からページ 3 へ移すことだった（NOTE では読み・候補・後続・結果・変換用の 7 つのバッファを CD00h 以降へ配置した）。

理由は、モジュールがポインタの高位バイトの bit6 でポインタの種別を判定しており、ページ 3 のポインタについてはステージングのコピー機構を通さず、バッファを直接参照するためである。ページ 3 は DIC 呼び出し中にスロット切り替えの対象にならないので、直接参照でも安全である。この変更で 2 回目セッションの変換は正常化し、その後の統合ビルドでも 2 セッションの往復検証を通過した。

一般化した指針は次のとおりである。

- **DIC のバッファはページ 3 に置くのが安全**である。Datapack は「ページ 2 か 3」を許容するが、実装によってはページ 2 側の受け渡しに 4.3 節のような問題が潜む。
- ページ 2 に置かざるを得ない場合は、単発の変換確認で済ませず、「Invoke → 変換 → Release → 再 Invoke → 変換」の往復まで検証すること。初回セッションだけでは検出できない問題がある。

## 4.5 学習と候補の非決定性

JE の学習はモジュール側の SRAM に保存され、プログラムの実行を跨いで効く。スパイクの実験では、同じ「かんじ」の変換でも、初回は候補 6 件（第一候補は寛治）だったものが、次の実行では候補 1 件（感じで固定）に変わっていた。

これは仕様であり、実機でも電池バックアップされた SRAM で同じことが起こる。エミュレータでも SRAM は永続化されるため、検証環境でも再現する。したがって、

- 検証コードは、候補の固定値（件数・順序・第一候補）を前提にしない。「期待する候補が集合に含まれるか」「表示された文字列と確定して保存されたバイト列が一致するか」で判定する。
- 検証の再現性が必要な場合は、SRAM の初期状態をそろえてから実行する。

## 4.6 エミュレータ環境の注意

エミュレータで観測した事象を、そのまま実機の挙動とみなしてはいけない例を挙げる。

二重 JE 構成（FS-A1ST 内蔵 JE と MSX-Write II カートリッジの併存）を fork openMSX で組んだところ、EXTBIO の列挙呼び出し自体が返ってこない事象が観測された（BASIC の USR 経由でも同様）。DOS 側でテーブルが得られた構成でも、Write モジュールへの Inquiry / Invoke は完了しなかった。一方、実機の単独モジュール構成（SX-2 ＋ MSX-Write JE が唯一のモジュール）では、NOTE の DIC フローは動作している（4.7 節）。

逆に、4.3 節のステージング問題は 2 つの異なるエミュレータ実装で再現した。「エミュレータで起きる事象は実機でも起きる」とも「起きない」とも一概には言えない。事象ごとに、複数の実装での再現や実機での確認といった裏取りが要る。

## 4.7 MSX-Write JE について

MSX-Write（および MSX-Write II）の JE モジュールについては、判明していることと、いないことを分けて記す。

判明していること:

- 二重 JE 構成で、EXTBIO の 2 番目のエントリとして観測された（ケーパビリティ F0h、スロット 01h、エントリ 4028h）。
- 実機の単独モジュール構成（SX-2、FS-A1WSX 相当 BIOS）では、NOTE の DIC フロー（Invoke、han_hira、henkan、kakutei2、Release）は動作し、変換・確定・保存まで到達した。
- BASIC の漢字入力（`CALL KANJI`）の FEP は、二重構成ではファームウェア側の JE が担っていた。Write カートリッジを外しても第一候補は同じ「感じ」であり、Write モジュールは BASIC 漢字ドライバからは使われていなかった。

実測できていないこと:

- **Write JE 単体の han_hira 返値 A の意味論**。エミュレータの二重構成ではモジュールに到達できず（4.6 節）、実機では表示側の問題（4.1 節）と切り分けができなかった。本書はこの点について断定しない。実機で Write JE を唯一のモジュールとして、3.4 節と同じプローブを当てることが今後の確認手順になる。
- 同様に、Write JE の henkan / kakutei2 の細部の返値（消費長の前提条件など）も単体測定は未実施である。

4.2 節の導出方式は、この未確定な領域に対する保険として位置づけられる。A の意味論が仕様どおりでも、そうでなくても、入出力から導く表示は壊れない。

# 第5章 仮想端末インターフェイス詳説

仮想端末インターフェイス（VT）は、変換の UI ロジックを JE 側に委ねるインターフェイスである。AP はウィンドウを用意してキーを振り分け、JE が返す STB（画面イメージ文字列）を描くだけで、日本語入力が成立する。本章では、Datapack とガイドブックの記述に、スパイクでの実測と KID.COM の実装解析を重ねて述べる。

## 5.1 VT の仕組み

VT のやり取りは次の形になる。

1. AP が画面にウィンドウを開き、変換を開始する（Clear）。
2. ユーザーの打鍵を JE が解釈し、読みの入力・変換・候補切替を進める。
3. 表示の更新が必要になるたび、JE は STB の形で「描くべき内容」を AP に返す。**JE が直接画面を描くことはない**。
4. 確定すると、AP は Get Result で確定文字列（Shift-JIS）を受け取る。

ウィンドウの場所は AP が選べる。通常は画面の最下行に取る（漢字 BASIC の漢字入力がこの姿である）が、中央でもよい。どのスクリーンモードでも使えるのは、この「表示は AP の仕事」という分担のためである。

注意点が 2 つある。

- JE は、ウィンドウ内の内容とカーソル位置が AP によって保存されている前提で動く。STB は差分（前回から変わった部分）だけが返ることもあるため、AP がウィンドウ領域を勝手に書き換えると表示が崩れる。
- STB の再描画は、変わらない部分を書き直さない工夫で体感速度が大きく変わる。MSX の漢字表示はビットマップ描画であり、1 打鍵ごとの全再描画は避けること（Datapack も同旨を注意している）。

## 5.2 機能一覧

共通部（1 Inquiry / 2 Invoke / 3 Release、第2章）に加えて、VT では次を使う。

|番号|名前|用途|備考|
|-|-|-|-|
|4|Clear|変換用バッファのクリア。入力開始時に呼ぶ|F キー文字列の設定も行われる（5.5 節）|
|5|Set TTB|再変換用テキスト（TTB）の設定|オプション。未サポートでは A = FFh|
|6|Dispatch|JE に処理を渡す|出力: A = ステータス、HL = STB のアドレス|
|7|Get Result|確定文字列の取得|出力: HL = 00h 終端の Shift-JIS 文字列|
|8|Get TTB|確定テキストの読み（TTB）の取得|オプション。未サポートでは HL が 0 へのポインタ|
|9|Inquire Window Size|ウィンドウ寸法の交渉|オプション|
|10|Conflict detect|キーの衝突検出|オプション。未サポートでは A = FFh の扱いに注意|

オプション関数は、無い実装があるものとして扱うこと。デフォルトのウィンドウは 1 行 × 半角 28 文字（全角 14 文字）であり、この大きさを使うなら Inquire Window Size は呼ばなくてよい。デフォルト以外を使う場合は関数 9 で交渉するが、全ての VT が希望の大きさをサポートする保証はない。VJE 系の注意として、Inquire Window Size を明示的に呼ぶことが推奨されている。

入力テキストの表示には必ずウィンドウ #0 を使う（複数ウィンドウに対応しない AP 向けの規定）。

## 5.3 Dispatch とステータス

Dispatch（関数 6）は、AP から JE に処理を渡す中心の関数である。JE は内部でキーキューからキーを読んで処理し、表示が必要になったとき、または制御を戻すべきときに返る。

|ビット|2|1|0|
|-|-|-|-|
|意味|変換終了|変換結果あり|STB を表示する|

戻り値 A のステータスは、3 つのビットを**それぞれ独立に**見て解釈する。

|ステータス|意味|
|-|-|
|000|キーが無視された、またはキー入力がなかった|
|001|入力中、または変換中（STB を表示）|
|010 / 011|部分確定をした（結果を取得。011 なら STB も表示）|
|100 / 101|変換が中断されて終了した|
|110 / 111|全確定した（結果を取得。111 なら STB も表示）|

例えばステータス 111 なら、「STB を表示し、Get Result で結果を得て、Dispatch のループを終える」という順序になる。AP の標準ループは次の形である（Datapack の C 例の骨格）。

1. キューを先読みし、先頭が JE のキーなら Dispatch を呼ぶ（キーの分担は 5.5 節）。
2. ステータスの bit0 が立っていれば、HL の指す STB を描く。
3. bit1 が立っていれば、Get Result（関数 7）で確定文字列を得る。
4. bit2 が立つまで 1〜3 を繰り返す。

スパイクでの実測では、打鍵 1 文字ごとに Dispatch が 1 回ずつ戻り（ステータス 001）、STB が未確定文字列の成長をそのまま返した。SPACE で変換されると STB の属性が変わり（5.4 節）、確定の打鍵ではステータス 07 が返って、Get Result で「感じ」のバイト列（8A B4 82 B6）が得られた。

## 5.4 STB 形式

STB は 00h 終端のバイト列で、表示内容と制御コードが混在する。

|バイト|意味|
|-|-|
|Shift-JIS 文字|カーソル位置に表示し、文字幅の分だけカーソルを進める（半角英数・半角カナを含む）|
|00h|STB の終わり|
|05h（^E）|カーソルより後ろの部分を消去|
|08h（^H）|カーソルの前の文字を消去し、カーソルを 1 文字後退させる|
|0Ch（^L）|ウィンドウを消去し、カーソルを先頭に戻す|
|12h（^R）＋ 長さ|カーソル位置から、続く 1 バイトで指定される長さだけ反転表示する|
|17h（^W）＋ 番号|続く 1 バイトで指定されるウィンドウを開く（オプション）|
|18h（^X）＋ x|カーソルを X 座標へ移動（1 始まり。0 はカーソル非表示）|
|19h（^Y）＋ y|カーソルを Y 座標へ移動（オプション）|
|1Ah（^Z）＋ 属性|属性を指定。属性バイトの上位 4 ビットが文字色、下位 4 ビットが背景色|
|上記以外の 00h〜0Fh|1 バイト読み飛ばす|
|上記以外の 10h〜1Fh|続く 1 バイトも読み飛ばす（システム予約）|

座標と長さは半角単位で指定される。属性（^Z）の使い分けは、資料では次の値が示されている。

|対象|属性|
|-|-|
|編集文字列（入力中）|1Fh|
|変換対象文字列|F5h|
|後続文節・未変換文節|1Fh|

スパイクの実測でも、入力中は属性 1Fh、変換後の文節は F5h で STB が返った。ただし、パレット設定を変えているソフトや SCREEN6 を使うソフトがこの値をそのまま使うと変な色になるため、その場合は自前の色に読み替えてよい（ガイドブックの注意）。

## 5.5 キーの分担

VT では、AP と JE が BIOS のキーバッファを共有し、**1 文字先読み**でキーを分担する。先読みは、GETPNT（F3FAh）の指すバイトを取り出さずに覗くことで行う（バッファに内容があるかは CHSNS（009Ch）で確認する）。

|キー|取る側|
|-|-|
|文字キー（スペースを含む）|JE|
|01h 始まりの 2 バイトコード（F1〜F5）|JE|
|コントロールコード（00h〜1Fh、7Fh。ただし 01h 始まりと F1〜F5 を除く）|AP|
|FFh 始まりのコード（F6〜F10）|AP|

分担の決まりを守らないと、同じキーを AP と JE が奪い合い、制御が往復し続ける（ハングする）ことがある。チェックが必要なのは、Clear の後、最初の Dispatch までの間である。それ以降は JE が処理する。

ファンクションキーの扱いにも決まりがある。Clear を呼ぶと、F キーの文字列が JE 用に設定される。

|キー|設定されるコード|
|-|-|
|F1〜F5|01h ＋ 31h〜35h|
|F6〜F10|FFh ＋ 36h〜3Ah（この値が入っている場合に F6〜F10 として処理される）|

元の F キー文字列を壊されたくない AP は、Clear の前に保存し、終わったら復元すること。

キーアサイン（変換キー、確定キー等）は MSX-JE の仕様では規定されず、**JE 実装ごとに異なる**。AP はアサインを決められず、「どのキーを JE に渡すか」の振り分けだけが AP の仕事である。参考として VJE-80A の割り当てを挙げる: SPACE = 変換／次候補、SHIFT+SPACE = 前候補、F1 = 入力モード切替、F2 = ひらがな変換、F3 = カタカナ変換、F4 = 半角変換、F5 = コード変換、CTRL+F5 = 全確定、RETURN = 部分確定、ESC = 段階的取消、BS / DEL = 削除、←→ = カーソル移動。Sony の実装では前候補が GRAPH キー、F2 がカタカナ変換になるなど、差があることが知られている。

## 5.6 KID.COM の実践

DOS 用のエディタ KID.COM（ver 1.02）が「どの JE でも動く」とされる理由は、その JE アクセスの解析で裏付けられた。KID の方式は、VT の教科書的な使い方である。

- **使う機能は 7 つだけ**: {1 Inquiry, 2 Invoke, 3 Release, 4 Clear, 6 Dispatch, 7 Get Result}。DIC の関数（40h〜50h）は一切呼ばない。han_hira を呼ばないので、返値 A の意味論（第4章の問題）とは無縁である。
- **モジュール選択はケーパビリティ走査**: `(cap AND 7) == 0` を満たす最初のエントリを採用する（2.7 節）。加えて、EXTBIO デバイス 17（MSX 漢字ドライバ）経由の経路も用意しており、デバイス 16 のモジュールとして登録されていない JE への到達も試みる。
- **ワークエリア**は Inquiry の MIN2 に自前のコンテキスト分を加え、TPA 上限の直下に確保する。JE 呼び出しは専用スタックに切り替えて行う。
- **入力の流れ**: JE 用の getkey が組成を管理する。組成の開始で Clear を呼び、以後はキーを Dispatch に渡す（モジュール自身がキューの先頭を消費する）。ステータス bit0 → STB を自前のターミナル風ウォーカで解釈して描く（制御コード 05h / 08h / 0Ch / 12h / 18h / 1Ah を処理し、2 バイト文字は自前のグリフ描画で出す）。bit1 → Get Result で確定文字列を得て、それを**通常入力として 1 文字ずつ再供給**する。組成中は GETPNT（F3FAh）を番兵値で凍結し、結果が尽きた時点で復元する。bit2 → 組成終了。
- **読みの表示は完全にモジュールの STB 任せ**であり、KID 自身はローマ字から読みを組み立てない。

つまり KID の移植性は、VT の契約（表示は STB、キーは JE が解釈、確定は結果文字列の受け取り）に徹することで得られている。実装差が入り込む余地が小さいのは、この割り切りのためである。

## 5.7 VT と DIC の使い分け

|観点|VT が向く場合|DIC が必要な場合|
|-|-|-|
|用途|「ちょっとした漢字入力」を足したいソフト全般。標準的な変換体験をそのまま使える|エディタ等で、文書のカーソル位置に未確定文字列を埋め込む表示が要る場合|
|キーアサイン|JE 実装のままでよい場合|ATOK 風など、AP 独自のアサインが要る場合|
|文節操作|不要な場合（STB の描画からしか分からない）|文節の移動・伸縮・候補選択を意味データで扱う場合|
|表示|ウィンドウ位置は選べるが、内容は STB の解釈の範囲内|完全な自前描画が要る場合|
|実装差への強さ|強い（5.6 節）|第4章の対策が要る|

MSX-NOTE が DIC を選んだのは、インライン表示と ATOK 風キーアサインが要求仕様だったためである。KID が VT を選んだのは、最下行の専用入力行という画面設計と「どの JE でも動く」ことの両立のためである。どちらも設計要求の帰結であり、インターフェース自体に優劣があるわけではない。自分の AP が文節構造を必要とするかどうかが、選択の分かれ目になる。

## 5.8 サンプル: 最小 FEP（vtdemo.asm）

VT の最小実装が、配布サンプルの `samples/ch05/vtdemo.asm` である。KID.COM の実践（5.6 節）に倣い、使う機能は Inquiry / Invoke / Release / Clear / Dispatch / Get Result の 6 つだけに絞った。モジュールの選択は「(cap & 7) == 0 の最初のエントリ」（2.7 節）、キーの分担はキューの先読みによる判定（5.5 節）、Dispatch のステータスはビットごとに独立に解釈する（5.3 節）。STB は最下行の 28 文字ウィンドウに描画し、制御コードのうち 05h / 08h / 0Ch / 18h を処理する。Clear が書き換える F キー文字列は、開始時に保存して終了時に復元する（5.5 節）。

![vtdemo.asm の実行画面。最下行ウィンドウで「かんじ」を変換したところ](images/vtdemo_conv.png)

簡略化した点も明記しておく。属性（1Ah）と反転（12h）は読み飛ばして通常表示にしているため、変換中の部分の見た目の区別は付かない。製品では 5.4 節の属性を自前の色に割り当てること。また、ウィンドウの行（22 行目）は定数にしてあるので、使用するコンソールの行数に合わせて調整が要る。確定結果は画面の結果エリアに残し、VTRES.TXT にも書き出す。

# 第6章 実装例

本章では、DIC クライアントの最小構成を、実際に動作するプログラムで示す。6.1 節のコードは配布サンプル `samples/ch06/jemini.asm` そのものであり、zma（Z80/R800 マクロアセンブラ）でそのままビルドして MSX-DOS2 上で実行できる。6.2 節では文節構築の反復を骨格で示し、6.3 節に実装上の指針をまとめる。

## 6.1 最小の DIC クライアント

検出 → Inquiry → Invoke → han_hira → henkan → ji_koho → kakutei2 → Release、という一巡である。読みは固定で、ローマ字 "kanji" を han_hira で読みに直し、第 1 候補で確定して結果を表示する。表示内容は JEMINI.TXT にも書き出すため、画面の読めない環境でも結果を確認できる。各処理に対応する節番号をコメントで示してあるので、本文と行き来しながら読んでほしい。

```
;=====================================================================
; jemini.asm - 最小の DIC クライアント (第6章)
;
; 検出 -> Inquiry -> Invoke -> han_hira -> henkan -> ji_koho
; -> kakutei2 -> Release、という DIC の一巡を実行する。
; 読みは固定で、ローマ字 "kanji" を変換して第 1 候補で確定し、
; 結果を表示する。表示内容は JEMINI.TXT にも書き出す。
;
; ビルド: zma jemini.asm JEMINI.COM   (MSX-DOS2 用 .COM)
;=====================================================================
		org		0x0100

BDOS		:= 0x0005
HOKVLD		:= 0xFB20
EXTBIO		:= 0xFFCA
RAMSLT3		:= 0xF344		; ページ 3 の RAM スロット

; バッファ類はページ 3 に置く (4.4 節)
MJETBL		:= 0xCC00		; EXTBIO テーブル (64 バイト)
JEWORK		:= 0xD000		; JE ワークエリア (2,560 バイト)
BUFCAND		:= 0xC800		; 候補バッファ
BUFREST		:= 0xC900		; 後続文節バッファ
BUFCONV		:= 0xCA00		; 読み (長さ付き形式)
BUFRES		:= 0xCE00		; 確定結果バッファ
LOGBUF		:= 0xB000		; 表示内容の控え (JEMINI.TXT 用)

;---------------------------------------------------------------------
start::
		ld		hl, LOGBUF
		ld		[logptr], hl
		ld		a, 1
		ld		[logon], a
		ld		hl, msg_title
		call	prt
		; --- 検出: HOKVLD bit0 (2.1 節) ---
		ld		a, [HOKVLD]
		rra
		jp		nc, no_ext
		; --- EXTBIO でモジュールテーブル取得 (2.2 節) ---
		ld		hl, MJETBL
		ld		b, 64
		xor		a, a
zloop:	ld		[hl], a
		inc		hl
		djnz	zloop
		ld		a, [RAMSLT3]
		ld		b, a
		ld		hl, MJETBL
		ld		de, 0x1000		; D = 16 (MSX-JE), E = 0
		push	hl
		call	EXTBIO
		pop		de
		or		a, a
		sbc		hl, de
		jp		z, no_je		; HL 不変 = JE 無し
		; --- 先頭エントリを採用し、DIC の有無を確認 (2.3 節) ---
		ld		a, [MJETBL]		; ケーパビリティ
		ld		[mod_cap], a
		and		a, 0x05
		jp		nz, no_dic		; 辞書インターフェイス無し
		ld		a, [MJETBL + 1]
		ld		[je_slot], a	; スタブへ転記
		ld		[mod_slot], a
		ld		hl, [MJETBL + 2]
		ld		[je_entry], hl	; スタブへ転記
		ld		[mod_entry], hl
		ld		hl, msg_mod
		call	prt
		ld		a, [mod_cap]
		call	prt_hex8
		ld		hl, msg_slot
		call	prt
		ld		a, [mod_slot]
		call	prt_hex8
		ld		hl, msg_entry
		call	prt
		ld		hl, [mod_entry]
		call	prt_hex16
		ld		hl, msg_h
		call	prt
		call	crlf
		; --- Inquiry (関数 1) (2.5 節) ---
		ld		a, 1
		call	call_je			; HL = MAX, DE = MIN, BC = MIN2
		ld		[in_max], hl
		ld		[in_min], de
		ld		[in_min2], bc
		ld		hl, msg_inq
		call	prt
		ld		hl, [in_min]
		call	prt_dec16
		ld		hl, msg_inq2
		call	prt
		ld		hl, [in_min2]
		call	prt_dec16
		call	crlf
		ld		hl, msg_inq3
		call	prt
		ld		hl, [in_max]
		call	prt_dec16
		call	crlf
		; --- Invoke (関数 2): ワークエリアは常に 2,560 バイト ---
		ld		de, 2560
		ld		a, 2
		call	call_je
		ld		a, 1
		ld		[invoked], a
		; --- han_hira (43h): "kanji" -> かんじ (3.4 節) ---
		ld		de, src_romaji
		ld		bc, BUFCONV
		ld		a, 0x43
		call	call_je			; A = 0 なら全変換
		ld		hl, msg_yomi
		call	prt
		ld		hl, BUFCONV
		call	prt_len
		call	crlf
		; --- henkan (47h): 変換開始 (3.6 節) ---
		ld		de, BUFCONV
		ld		a, 0x47
		call	call_je
		or		a, a
		jr		z, no_cand		; A = 0 は候補なし
		; --- ji_koho (48h): 第 1 候補を得る ---
		ld		de, BUFCAND
		ld		bc, BUFREST
		ld		a, 0x48
		call	call_je
		or		a, a
		jr		z, no_cand
		ld		[cand_no], a
		ld		hl, msg_cand
		call	prt
		ld		hl, BUFCAND
		call	prt_len
		call	crlf
		; --- kakutei2 (4Dh): 先頭文節を第 1 候補で確定 (3.7 節) ---
		ld		a, [cand_no]
		ld		e, a
		ld		bc, BUFRES
		ld		a, 0x4D
		call	call_je			; A = 消費した読みバイト数
		ld		[consumed], a
		ld		hl, msg_kakutei
		call	prt
		ld		hl, BUFRES
		call	prt_len
		ld		hl, msg_shouhi
		call	prt
		ld		a, [consumed]
		call	prt_dec8
		ld		hl, msg_byte
		call	prt
		call	crlf
		jr		release
no_cand:
		ld		hl, msg_nocand
		call	prt
release:
		; --- Release (関数 3): 単一の終了経路で必ず呼ぶ (2.8 節) ---
		ld		a, [invoked]
		or		a, a
		jr		z, exit
		ld		a, 3
		call	call_je
		ld		hl, msg_rel
		call	prt
exit:
		call	log_save
		ld		c, 0x00
		jp		BDOS
no_ext:
		ld		hl, msg_noext
		call	prt
		jr		exit
no_je:
		ld		hl, msg_noje
		call	prt
		jr		exit
no_dic:
		ld		hl, msg_nodic
		call	prt
		jr		exit

;=====================================================================
; JE 呼び出しスタブ (2.4 節)
; in: A = 関数番号, BC / DE = パラメータ
;=====================================================================
call_je:
		ld		hl, JEWORK
		rst		0x30
je_slot:
		db		0
je_entry:
		dw		0
		ret

;=====================================================================
; 表示ルーチン (画面 + ログへの二重出力)
;=====================================================================
putc:
		push	hl
		push	de
		push	bc
		push	af
		ld		e, a
		ld		c, 0x06			; _DIRIO (出力)
		call	BDOS
		pop		af
		ld		e, a
		ld		a, [logon]
		or		a, a
		jr		z, pc_done
		ld		hl, [logptr]
		ld		[hl], e
		inc		hl
		ld		[logptr], hl
pc_done:
		pop		bc
		pop		de
		pop		hl
		ret

; 文字列出力: HL = 00h 終端文字列
prt:
		ld		a, [hl]
		or		a, a
		ret		z
		call	putc
		inc		hl
		jr		prt

; 長さ付き形式の文字列出力: HL = バッファ
prt_len:
		ld		a, [hl]
		or		a, a
		ret		z
		ld		b, a
		inc		hl
pl_1:	ld		a, [hl]
		call	putc
		inc		hl
		djnz	pl_1
		ret

crlf:
		ld		a, 0x0D
		call	putc
		ld		a, 0x0A
		call	putc
		ret

prt_hex8:
		push	af
		srl		a
		srl		a
		srl		a
		srl		a
		call	prt_hex4
		pop		af
		and		a, 0x0F
prt_hex4:
		add		a, '0'
		cp		a, '9' + 1
		jr		c, ph4_ok
		add		a, 7
ph4_ok:	call	putc
		ret

prt_hex16:
		ld		a, h
		call	prt_hex8
		ld		a, l
		call	prt_hex8
		ret

prt_dec8:
		ld		h, 0
		ld		l, a
		jr		prt_dec16

prt_dec16:
		xor		a, a
		ld		[pd_started], a
		ld		de, 10000
		call	pd_dig
		ld		de, 1000
		call	pd_dig
		ld		de, 100
		call	pd_dig
		ld		de, 10
		call	pd_dig
		ld		a, l
		add		a, '0'
		call	putc
		ret
pd_dig:
		ld		a, '0' - 1
pd_d1:	inc		a
		or		a, a
		sbc		hl, de
		jr		nc, pd_d1
		add		hl, de
		cp		a, '0'
		jr		nz, pd_d2
		ld		a, [pd_started]
		or		a, a
		ret		z
		ld		a, '0'
pd_d2:	push	hl
		push	de
		call	putc
		ld		a, 1
		ld		[pd_started], a
		pop		de
		pop		hl
		ret

;=====================================================================
; ログを JEMINI.TXT に保存する (DOS2 ハンドル API)
;=====================================================================
log_save:
		ld		hl, LOGBUF
		ld		de, [logptr]
		or		a, a
		sbc		hl, de
		ld		a, l
		cpl
		ld		l, a
		ld		a, h
		cpl
		ld		h, a
		inc		hl
		ld		[loglen], hl
		; _CREATE (44h): A = アクセスモード (2 = 書き込み),
		; B = 作成フラグ (0)。戻り値: A = 0 で成功、B = ハンドル
		ld		de, fname
		ld		a, 2
		ld		b, 0
		ld		c, 0x44			; _CREATE
		call	BDOS
		or		a, a
		ret		nz
		ld		a, b
		ld		[loghdl], a
		ld		hl, [loglen]
		ld		de, LOGBUF
		ld		a, [loghdl]
		ld		b, a
		ld		c, 0x49			; _WRITE
		call	BDOS
		ld		a, [loghdl]
		ld		b, a
		ld		c, 0x45			; _CLOSE
		call	BDOS
		ret

;=====================================================================
; データ
;=====================================================================
msg_title:	db	"最小の DIC クライアント", 0x0D, 0x0A, 0
msg_noext:	db	"拡張 BIOS がありません。", 0x0D, 0x0A, 0
```

## 6.2 文節を 1 つずつ確定するループ

文節配列を構築する反復（3.7 節）の骨格を示す。読みバッファの詰め直しや文節記録の保持は実装依存のため、呼び出しの連鎖とポインタの前進に絞ってある。

```
; 文節構築ループ (骨格)
;   rd_len: 残りの読みの長さ (バイト数)。読みは rd_buf に
;   長さ付き形式で入っているものとする。
build_loop:
        ld      a, [rd_len]
        or      a, a
        ret     z               ; 読みが尽きたら終わり
        ; henkan (47h): 残りの読み全体を変換
        ld      de, rd_buf
        ld      a, 0x47
        call    call_je
        or      a, a
        jr      z, build_none   ; 候補なしの場合の方針 (読みを
                                ; そのまま 1 文節とする等) を決める
        ; ji_koho (48h) の列挙で、選択中の候補まで進めて同期
        ;   (この同期が無いと kakutei2 の消費長が返らない: 3.7 節)
        ld      de, BUFCAND
        ld      bc, BUFREST
        ld      a, 0x48
        call    call_je
        ; kakutei2 (4Dh): 先頭文節を選択中の候補で確定
        ld      e, [sel_no]     ; 候補の通し番号
        ld      bc, BUFRES
        ld      a, 0x4D
        call    call_je         ; A = 消費した読みバイト数
        ; 文節記録 {読み範囲, 候補一覧, 選択中候補, BUFRES の文字列}
        ; を保存し、読みポインタを A バイト進めて rd_buf を詰め直す
        ;   (消費長をメモリ経由で BC に組み、DE は最後に設定する
        ;    こと。レジスタの潰し合いによる移送ミスを避けるため)
        jr      build_loop
build_none:
        ; 候補なしの方針をここに実装する
        ret
```

Enter による全文確定では、この反復で得た文節ごとの確定文字列を連結する。各文節の選択中候補（および 3.9 節の上書きテキスト）を尊重するため、kakutei1 の一括確定は使わない。

## 6.3 実装上の指針

実運用で確認した指針をまとめる。詳細は各節を参照のこと。

- **Invoke は起動時に 1 回、Release は単一の出口で**（2.6 節、2.8 節）。Invoke 前の終了経路では Release は不要であり、Invoke 後の全ての経路は cleanup に合流させる。
- **DIC バッファはページ 3 に置く**（4.4 節）。ページ 2 のバッファには、実装によっては 2 回目のセッションで顕在化する問題が潜む。
- **返値 A の解釈は最小限に**。henkan の A は「0 か否か」だけを見る（3.6 節）。kakutei2 の消費長は、ji_koho の列挙で同期させた後にのみ使う（3.7 節）。han_hira の A は表示に使わず、入出力から末尾を導く（4.2 節）。
- **JE の使用開始時に入力キューをドレインする**（2.8 節）。残留キーが変換開始直後に流れ込む事象を観測した。
- **候補は学習で変わるものとして扱う**（4.5 節）。候補の固定値を前提にした表示・検証はしない。
- **文節の伸縮は再変換で実現する**（3.8 節）。専用関数は無い。
- **文字種変換の関数の対象を取り違えない**（3.3 節、3.9 節）。特に、全角ひらがなのカタカナ化は hira_kata（45h）単独で行う。
