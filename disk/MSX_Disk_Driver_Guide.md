# 第1章 概要

## 1.1 本書の目的

本書は、MSX-DOS および MSX-DOS2 のカーネルが、ディスクドライバに対して何を要求するのかをまとめた資料である。対象とする読者は、MSX のディスクインターフェースを新たに実装する人——とりわけ、実ドライブの代わりにディスクイメージを扱うエミュレーターや、FPGA 上の新しいストレージ装置を MSX2++ のような後継機へ接続しようとする人——である。

MSX のディスク環境は、カーネルとドライバが 1 本の ROM の中で明確に分業している。カーネルはファイルシステムと DOS の機能全体を担い、ドライバは FDC（フロッピーディスクコントローラ）や相当するハードウェアを叩く部分だけを担う。両者の境界は小さく、初期化時に呼ばれる数本のルーチンと、4000H 台の公開エントリーテーブルに集約されている。この境界さえ正しく実装すれば、カーネル側は相手が実ドライブでもディスクエミュレーターでも区別できない。本書は、その境界の仕様を実機 ROM の解析で裏付けながら記述する。

## 1.2 カーネルとドライバの二層構造

MSX のディスク ROM（DiskBIOS）は 16KB の ROM で、ページ 1（4000H〜7FFFH）に配置される。その内部は次の 2 層からなる。

|層|役割|所在の目安|
|-|-|-|
|カーネル|ファイルシステム、DOS/BASIC のディスク機能、公開エントリーのうち機種非依存の部分、ワークエリア管理|4000H〜73FFH|
|ドライバ|FDC の初期化と制御、セクタの読み書き、ディスク交換の検出、物理フォーマット|7400H〜7FFFH（約 3KB）|

この分担は、ハードウェアの異なる 2 機種の ROM を比較すると鮮明に見える。本書の解析では、Sony HB-F1XDJ（FDC は WD2793）と Panasonic FS-A1WSX（FDC は TC8566AF）のディスク ROM を全バイト比較し、全体の 81.3% がバイト単位で一致すること、差異の大部分が 7400H 以降のドライバ領域に集中することを確認した。カーネルは機種が変わっても（細部の版違いを除いて）そのまま使われ、ドライバだけがハードウェアごとに差し替えられる。つまり「カーネルがドライバに要求する仕様」は、機種を超えて安定した契約として存在している。

逆に言えば、ドライバ領域の内側——FDC のレジスタをどの順でどう叩くか——はカーネルから一切見えない。本書では FDC の詳細には立ち入らず、境界に現れる範囲でのみ触れる（6.2 節）。

## 1.3 本書の材料と記述の立場

本書の記述は、次の材料の照合に基づく。

|材料|内容|
|-|-|
|HB-F1XDJ ディスク ROM|Sony 製。FDC は WD2793。openMSX の既知ダンプとは一部異なるリビジョン|
|FS-A1WSX ディスク ROM|Panasonic 製。FDC は TC8566AF（レジスタは 7FF8H 起点）|
|MSX-DOS2 カートリッジ ROM|ASCII 製 MSX-DOS2（カーネル バージョン 2.20）。DOS2 側からのドライバ利用を調べるために使用|
|MSXテクニカルガイドブック 第四版|ASCAT 編集部（1992）。ディスクインターフェイス ROM 内ルーチンの入出力仕様の出典|
|MSX-Datapack|アスキー。DiskBIOS の初期化手順とワークエリア配置の出典|

記述の立場は次のとおりである。

- 仕様の最終判断は、実 ROM のコードがどう振る舞うかに置く。文献（テクニカルガイドブック、以下 tg45）と実コードが食い違う場合は実コードを正とし、食い違い自体を注記する。実際に、tg45 の記述と逆だった事例（F33FH の意味、3.4 節）や、tg45 が名前を与えていないエントリーに実コードから名前を確定した事例（401FH、4.7 節）がある。
- 裏が取れなかった事項は「未確定」と明記し、推測と事実を混ぜない。未確定事項は付録 A.4 に集約した。
- ROM のコードそのものは本書に掲載しない。エントリーテーブルのアドレスやジャンプ先のような事実データと、振る舞い・規約の記述に限る。

## 1.4 本書の構成

第 2 章では DiskBIOS の構造——ROM ヘッダ、エントリーテーブル、ワークエリアと DPB——を述べる。第 3 章では電源投入から DOS が使えるようになるまでの初期化の流れを、カーネルとドライバのやり取りの順に追う。第 4 章は公開エントリー各々の入出力仕様の詳説である。第 5 章では MSX-DOS2 の下でこの境界がどう扱われるかを述べる。第 6 章は、新しいドライバを実装するための指針とチェックリストである。第 7 章では、既存カーネルに自作ドライバを接続して ROM ディスクを実現する実働サンプルを、コードの解説とともに示す。付録には、2 機種の ROM の差分解析の記録と未確定事項の一覧を置く。

# 第2章 DiskBIOS の構造

## 2.1 ROM ヘッダとエントリーテーブル

ディスク ROM は通常のカートリッジ ROM と同じヘッダを持ち、ID「AB」に続いて INIT（576FH）が登録されている。STATEMENT（6576H）は OEM 固有ステートメントの入口で、末尾でドライバ側の OEMSTA へジャンプする。DEVICE と TEXT は使われず 0 である（ディスクは BASIC のデバイス機構とは別の経路で接続される）。

ヘッダ直後の 4010H からは、ドライバとの境界になる公開エントリーテーブルが並ぶ。実 ROM から読み取った内容は次のとおりである。ジャンプ先は F1XDJ／WSX の順に示す。

|アドレス|名前|ジャンプ先|実装側|
|-|-|-|-|
|4010H|DSKIO|751EH／7495H|ドライバ|
|4013H|DSKCHG|78BAH／77F3H|ドライバ|
|4016H|GETDPB|7943H／7833H|ドライバ|
|4019H|CHOICE|795DH／784EH|ドライバ|
|401CH|DSKFMT|79A0H／7C80H|ドライバ|
|401FH|MTROFF|7DE2H／775AH|ドライバ|
|4022H|（ワークエリア初期化）|5B3AH／5B3AH|カーネル|
|4025H|FORENT|SCF ＋ JP 60B1H|カーネル|
|4029H|MTOFF|JP 620DH|カーネル|
|402DH|GETSLT|JP 5FB3H|カーネル|
|4030H|（(F34BH) の取得）|LD HL,(F34BH) ＋ RET|カーネル（インライン）|

ここから分かる重要な事実は、**機種依存のジャンプは 4010H〜401FH の 6 本だけ**だということである。4022H 以降の入口はすべてカーネル内部を指し、2 機種でバイト単位まで一致する。FORENT（4025H）はジャンプ命令ではなく、キャリーフラグをセットしてカーネルの共通処理（60B1H）へ飛ぶ 4 バイトの入口になっている。この作りには意味があり、4.8 節で説明する。

なお 4022H と 4030H には tg45 でも名前が与えられていない。本書でも名前は付けず、アドレスで呼ぶ。

## 2.2 2 機種の差分が示す境界

2 機種の ROM の差分は 3,066 バイトで、その分布は次のとおりである。

|範囲|差分の性質|
|-|-|
|4011H〜4021H|エントリーテーブルのジャンプ先アドレス（ドライバの配置差）|
|53D8H 付近（6 バイト）|カーネル内のコール順序の入れ替え（版差）|
|6576H〜65B0H（49 バイト）|STATEMENT 入口ブロック内の版差（付録 A.2）|
|5770H〜5891H の一部|INIT 内のドライバ呼び出し先と定数（MYSIZE 等）|
|7405H〜7FC5H|ドライバ領域そのもの|
|7FE0H 以降|ROM 末尾の詰め物の差（コードとしての意味なし）|

カーネル共通部の中にも小さな版差はあるが、ドライバとの境界の形——入口の並び、呼び出しの順序、レジスタ規約——は両機種で完全に同一である。本書の記述はこの共通部分に基づいており、機種固有の値はそのつど両機種分を併記する。

## 2.3 ワークエリアの配置

DiskBIOS のワークエリアは RAM の F1C9H 以降に置かれる。初期化時の割り当ては、上位メモリから下向きに伸びる alloc の仕組みで行われ、レイアウトは大まかに次のようになる（MSX-Datapack 第 2 部第 2 章の図に基づく）。

|領域|内容|
|-|-|
|固定ワークエリア（F380H が上限）|カーネルが使う固定領域。F1C9H〜F37FH を 0 クリアして使う|
|ドライバワークエリア|インターフェースごとに MYSIZE バイト。ドライバが自由に使う|
|DPB 群|ドライブごとに 21 バイト|
|セクタバッファ類|$SECBUF（F34DH）、$BUFFER（F34FH）、$DIRBUF（F351H）へのポインタが指す領域。H.RUNC のタイミングで確保される|
|FAT バッファ|ドライブごとに 1 つ。DPB の +19 から指される|

ドライバに関係する主要なワークエリアは次のとおりである。

|アドレス|名前|内容|
|-|-|-|
|F33FH|—|現在アクセス中の論理ドライブ番号。カーネルのディスパッチ部がドライバ呼び出しの直前に設定する。INIT 中は CONTROL キーの状態の受け渡しにも使われる（3.4 節）|
|F34BH|—|DOS システム本体の開始アドレス。4030H の入口が HL に返す|
|F351H|$DIRBUF|ディレクトリ用バッファへのポインタ|
|F355H|$DPBLIST|DPB チェーンの先頭ポインタ|
|FB21H|DRVTBL|インターフェースごとの [ドライブ数, スロット番号] の表（最大 4 組）|
|FB29H|—|タイマ割り込み配信テーブル。インターフェースごとに 3 バイトの JP 命令が並ぶ（3.5 節）|
|FD99H|DISKID|ディスクインターフェースの登録カウンタ。0 = 未登録、FFH = 無効化|

ドライバ自身のワークエリアの内部レイアウトは完全にドライバの自由である。実例でも、F1XDJ と WSX では物理ドライブ数の記録位置（ワークエリア先頭からのオフセット）が異なっている（+8 と +7）。カーネルはドライバワークエリアの中身を一切解釈しない。

## 2.4 DPB とメディアテーブル

カーネルはドライブごとに DPB（Drive Parameter Block、21 バイト）を保持し、ファイルアクセスのたびに参照する。DPB の構造は次のとおりである。

フィールドの並びは MSX-Datapack の DPB 構造体の定義と一致し、各フィールドの値は実機のメディアテーブルのバイト列からも裏付けられる（メディア F9H＝2DD・9 セクタの場合の値を括弧内に示す）。

|オフセット|内容|書く側|
|-|-|-|
|+0|ドライブ番号（0 = A ドライブ）|カーネル|
|+1|メディア ID（F9H）|ドライバ（GETDPB）|
|+2〜+3|セクタ長（0200H）|ドライバ（GETDPB）|
|+4|ディレクトリマスク（セクタ長/32 − 1 ＝ 0FH）|ドライバ（GETDPB）|
|+5|ディレクトリシフト（4）|ドライバ（GETDPB）|
|+6|クラスタマスク（1 クラスタのセクタ数 − 1 ＝ 1）|ドライバ（GETDPB）|
|+7|1 クラスタのセクタ数（2）|ドライバ（GETDPB）|
|+8〜+9|FAT の先頭セクタ番号（1）|ドライバ（GETDPB）|
|+10|FAT の複製数（2）|ドライバ（GETDPB）|
|+11|ルートディレクトリのエントリ数（112）|ドライバ（GETDPB）|
|+12〜+13|データ領域の先頭セクタ番号（14）|ドライバ（GETDPB）|
|+14〜+15|最大クラスタ番号（714）|ドライバ（GETDPB）|
|+16|FAT 1 個分のセクタ数（3）|ドライバ（GETDPB）|
|+17〜+18|ルートディレクトリの先頭セクタ番号（7）|ドライバ（GETDPB）|
|+19〜+20|FAT バッファへのポインタ|カーネル（後から設定）|

ドライバが書くのは +1〜+18 の 18 バイトであり、その値はドライバが ROM 内に持つ**メディアテーブル**からコピーされる。メディアテーブルは、メディア ID（FAT の先頭バイト、F8H〜）ごとに 18 バイトのエントリを並べたもので、GETDPB は (メディア ID − F8H) × 18 バイト目から 18 バイトを DPB+1 へ転送するだけのルーチンである。実機のエントリ数は F1XDJ が 4 種（F8H〜FBH）、WSX が 8 種（F8H〜FFH）で、扱えるメディアの種類はドライバが決める。なお F8H〜FBH のエントリは両機種でほぼ共通であり、差は FBH のデータ領域先頭セクタ（F1XDJ は 10、WSX は 12）にだけある。

初期化時に各ドライブへコピーされるデフォルト DPB のテンプレート（DEFDPB）もドライバが持つ。実機では DEFDPB はメディアテーブルの中に重ねて配置されており、「ドライブ番号 0 のバイト ＋ メディア F9H（2DD・9 セクタ）のエントリ ＋ 2 バイト」という形で、21 バイトのテンプレートをテーブルと共有している。初期化直後の DPB はこのデフォルト値であり、実際にディスクが読まれる段階で GETDPB により本物の値へ差し替えられる。

# 第3章 初期化の流れ

## 3.1 INIT の全体像

ディスク ROM の初期化は、ROM ヘッダの INIT（576FH）から始まる。INIT はカーネル側の処理だが、その中でドライバ側のルーチンを 3 本——INIHRD、DRIVES、INIENV——呼び、ドライバが持つ定数（MYSIZE、SECLEN、DEFDPB）を参照する。ドライバ実装者にとって、初期化の契約はこの 3 本と 3 定数に集約される。

INIT の処理は、MSX-Datapack 第 2 部第 2 章に疑似コード（リスト 2.2）として掲載されており、実 ROM のコードもそれと一致する。大まかな流れは次のとおりである。

1. INIHRD を呼ぶ（ハードウェアの初期化。マスター／スレーブの判定より前）
2. DISKID（FD99H）を見て分岐する。80H 以上なら何もせず戻る。0 でなければスレーブ登録（3.6 節）へ
3. マスター登録：拡張 BIOS の土台を用意し、固定ワークエリアと自ドライバのワークエリアを確保して初期化する
4. 自インターフェースのドライブを登録する（DRIVES → DPB の生成 → INIENV）
5. DISKID を 1 増やして戻る

この後、DOS の起動時には H.RUNC のタイミングでセクタバッファや FAT バッファが確保され、ブートセクタが読まれる（3.7 節）。

## 3.2 マスター登録の手順

マスター登録（DISKID = 0 のとき）でカーネルが行う処理は次のとおりである。

- HOKVLD（FB20H）の bit0 を立て、EXTBIO テーブル（FFCAH、15 バイト）を RET 命令で初期化する
- HIMEM の残量を検査し、不足していれば登録を諦める
- キーボード行 6 を読み、SHIFT キーが押されていればビープ音を鳴らし、DISKID = FFH として戻る（ディスク機能の無効化。ドライバ側に特別な処理はない）
- 固定ワークエリア（F1C9H〜F37FH）とドライバワークエリア（MYSIZE バイト）を確保し、固定側を 0 クリア、ディスク関係のフック群を RET で初期化する
- CONTROL キーの状態を読み、F33FH へ保存する（DRIVES への受け渡しに使う。3.4 節）
- H.RUNC（FECBH）に、自 ROM の処理へ入る RST 30H スタブを設定する
- GETSLT（402DH）で自スロット番号を取得し、FE CCH へ保存する

ここで注目すべきは、ドライバワークエリアの確保量がドライバ自身の宣言（MYSIZE）に委ねられている点である。カーネルはその中身を解釈せず、初期化もしない。ゼロクリアが必要なら INIENV でドライバ自身が行う（実機の両ドライバともそうしている）。

## 3.3 INIHRD の契約

INIHRD は INIT の最初に、引数なしで呼ばれる。役割は FDC とドライブのハードウェア初期化であり、戻り値に意味はない。

実機の実装は次のような内容である。F1XDJ は FDC へ Force Interrupt コマンドを発行してリセットし、各ドライブを選択してシークとリストアを行い、トラック 0 に到達することを確認して、最後にドライブをデセレクトする。WSX は一時的なパラメータブロックをスタック上に組み、FDC の初期化コマンド列を発行する。WSX では INIHRD の末尾部分が 401FH（MTROFF）の飛び先と共用になっている。

エミュレーターのような、初期化すべき実ハードウェアを持たないドライバでは、INIHRD は最小限の体裁（内部状態の初期化だけ）でよい。ただし「呼ばれる時点ではワークエリアの確保がまだ済んでいない」ことには注意が要る。INIHRD の段階では自ドライバのワークエリアは存在しないため、状態は ROM 側の静的領域かレジスタで完結させ、ワークエリアへの書き込みは INIENV 以降に回すのが安全である。

## 3.4 DRIVES の契約

DRIVES は、自インターフェースにぶら下がるドライブを数えて登録台数を決めるルーチンである。呼び出しの規約は独特で、引数の一部がフラグで渡される。

|項目|内容|
|-|-|
|入力 A|既に登録済みの総ドライブ数|
|入力 Z フラグ|CONTROL キーが押されていれば Z セット（カーネルは呼び出し直前に F33FH を AND して Z を作る）|
|出力 L|このインターフェースで登録する論理ドライブ数|
|保存すべきもの|AF（実機の両ドライバとも PUSH/POP で保存している）|

実機の両ドライバの振る舞いは次のとおりで、契約の解釈が一致している。

- まず 2 台目のドライブを実際にプローブする（F1XDJ はドライブ 1 を選択してリストアし、BUSY の解除をタイムアウト付きで待つ。WSX は FDC コマンドの成否で判定する）
- 物理ドライブ数を、ドライバワークエリア内の私用フィールドに記録する（記録位置はドライバの自由。F1XDJ は +8、WSX は +7）
- 戻り値 L は、CONTROL キーが押されていれば 1（ドライブを 1 台だけに制限する起動オプション）、そうでなければ 2 とする。**物理 1 台でも 2 を返す**のが要点で、これは DOS の 2 ドライブシミュレーション（1 台のドライブで A:/B: を切り替えて使う仕組み）を有効にするためである。物理台数を記録しておくのは、後で DSKFMT などが「本当は 1 台しかない」ことを知るためである

カーネルは戻り値 L を総数に加え、全体が 8 台を超えないよう制限して、DRVTBL（FB21H）に [台数, スロット番号] を記録する。続いてドライブごとに 21 バイトの DPB を確保し、DEFDPB をコピーする。

なお F33FH について、tg45 は「CONTROL キーが押されていれば 2 が入る」と述べているが、実コードではキーボード行の読み値（アクティブロー）がそのまま入るため、**2 = 押されていない、0 = 押されている**が正しい。DRIVES へはこの値の AND 結果が Z フラグとして渡るので、ドライバ側は F33FH の数値ではなく Z フラグだけを見るべきである。

## 3.5 INIENV とタイマ配信

INIENV はドライブ登録の最後に呼ばれ、ドライバの環境初期化を行う。実機の実装は 2 つの仕事をしている。

1. ドライバワークエリアの先頭数バイトを 0 クリアする（F1XDJ は 8 バイト、WSX は 7 バイトと追加のフラグ設定）
2. タイマ割り込みで定期的に呼ばれるルーチンのアドレスを、カーネルの配信テーブル（FB29H）へ登録する

配信テーブルはインターフェースごとに 3 バイトの JP 命令が並ぶ形で、カーネルの H.TIMI 処理が登録済みの各エントリを、自スロットへの CALSLT で順に呼ぶ。ドライバはこの定期呼び出しを、モーターの自動停止に使う。WSX の登録ルーチンはワークエリア内のモーター停止カウンタ（3 バイト）をデクリメントし、期限が来たらモーター停止の印を立てる。F1XDJ の登録先はカーネルの配信処理へそのままジャンプするだけのセルで、この機種ではカウンタを持たない（モーター制御の方法が FDC 側の事情で異なるためと見られる）。

エミュレーター実装ではモーターの概念自体が不要なことが多いが、配信テーブルへの登録そのものは行い、中身は RET だけのルーチンを指すのが無難である。登録しないと、テーブルに前の内容が残る危険がある。

## 3.6 スレーブ登録と複数インターフェース

2 つ目以降のディスクインターフェースの INIT（DISKID が 0 でないとき）は、スレーブ登録の経路を通る。マスター側の土台（固定ワークエリアやフック群）は既に存在するので、処理は軽い。

- DRVTBL を走査して既登録ドライブ数を数え、8 台に達していれば登録しない
- 自ドライバのワークエリア（MYSIZE バイト）を確保し、SLTWRK にリンクする
- 自ドライバの SECLEN と現在の最大セクタ長（F6ABH）を比較し、大きい方を残す
- マスター登録と同じく DRIVES → DPB 生成 → INIENV の順で自ドライブを登録する

INIHRD はスレーブでも（DISKID の判定より前に）呼ばれる。複数インターフェースが存在するシステムでは、各インターフェースの INIT がそれぞれ INIHRD を実行することになる。

## 3.7 起動：H.RUNC からブートセクタへ

初期化が終わった後、DOS の起動は H.RUNC を経由する。カーネルはこのタイミングでセクタバッファ（$SECBUF、$BUFFER、$DIRBUF）と各ドライブの FAT バッファを確保し、DPB の +19 に FAT バッファへのポインタ（バッファ先頭の 1 バイト前を指す、カーネル側の慣習）を設定する。

ブートセクタの読み出しでは、デフォルト DPB のメディア ID（DEFDPB+1 の値、実機では F9H）が使われる。カーネルは PHYDIO（メイン ROM の 0144H）を介してドライブ 0 のセクタ 0 を $DIRBUF へ読み、先頭 256 バイトを C000H へ転送し、先頭バイトが EBH か E9H（ジャンプ命令）であることを確認してから、転送したブートコードへ制御を移す。この命令列はカーネル内の 5AE7H にある（ニーモニック表の 5AE2H 行との関係は付録 A.3 で述べる）。

ドライバの立場では、起動時に必要なのは「デフォルトメディアのセクタ 0 が DSKIO で読めること」だけである。メディア ID が F9H で宣言されている以上、少なくとも 2DD・9 セクタ形式のイメージは起動直後から読めなければならない。

# 第4章 公開エントリー詳説

## 4.1 カーネル側の呼び出し方

各エントリーの仕様に入る前に、カーネルがドライバをどう呼ぶかを押さえておく。カーネルのディスパッチ部（6052H〜）は、論理ドライブ番号から対象インターフェースを引く共通処理を持っている。

1. DRVTBL（FB21H）を走査し、各インターフェースのドライブ数を引いていくことで、論理ドライブを「インターフェース内の局所ドライブ番号（0 始まり）」と「そのインターフェースのスロット番号」に変換する
2. 論理ドライブ番号を F33FH へ保存する（ドライバがプロンプト表示などに使える）
3. IX にエントリーアドレス（4010H 等）、IY にスロット番号を入れて CALSLT（メイン ROM の 001CH）で呼ぶ

したがってドライバの各エントリーは、**A レジスタには局所ドライブ番号が入った状態で、自スロットが選択された状態で**呼ばれる。レジスタ規約は PHYDIO（メイン ROM の隠し BIOS、0144H）のものと同一に設計されており、カーネルは DSKIO については PHYDIO とまったく同じ呼び出し方をする。

## 4.2 DSKIO（4010H）

セクタ単位の読み書きを行う、ドライバの中核である。入出力は PHYDIO の規約そのものである。

|項目|内容|
|-|-|
|入力 Cy|セット = 書き込み、リセット = 読み込み|
|入力 A|ドライブ番号（インターフェース内、0 始まり）|
|入力 B|転送するセクタ数|
|入力 C|メディア ID|
|入力 DE|先頭の論理セクタ番号|
|入力 HL|転送先（DMA）アドレス|
|出力 Cy|リセット = 成功、セット = 失敗|
|出力 A|失敗時のエラーコード|
|出力 B|失敗時、転送できなかった残りセクタ数|

振る舞いの要点は次のとおりである。

- メディア ID（C）は、ドライバがセクタ配置（トラック／セクタへの分解方法）を決めるために使う。カーネルは DPB のメディア ID をそのまま渡す
- エラーコードは DOS 共通の番号で返す。実機のドライバは FDC のステータスの各ビットをこの番号へ変換している。F1XDJ の読み書き処理で観測された対応は、ノットレディ → 2、書き込み保護 → 0、レコード未検出 → 8、データエラー（CRC）→ 4、その他の失敗 → 12 で、tg45 のエラー番号表（0 = 書き込み禁止、2 = ノットレディ、4 = データエラー、6 = シークエラー、8 = レコードが見つからない、10 = 書き込みエラー、12 = その他のエラー）と整合する
- 部分的に転送できた場合は、残りセクタ数を B に残して戻る。カーネルはこの値を見て再試行やエラー報告を行う
- 割り込みの可否や他レジスタの保存については tg45 の PHYDIO の項に作法がまとめられている。少なくとも IX、IY は呼び出し側（カーネル）が使っているため、壊す場合は退避が要る

エミュレーター実装では、DSKIO は「メディア ID から決まる CHS 配置で、論理セクタ番号をイメージ内のオフセットへ変換し、B セクタ分を読み書きする」処理になる。エラーは、イメージが存在しない場合や範囲外アクセスの場合に、Cy セット＋A に適当なコード（例えば 8 や 12）を返せばよい。

## 4.3 DSKCHG（4013H）

ディスクが交換されたかどうかをカーネルへ伝える。カーネルはファイルアクセスの要所でこれを呼び、戻り値によって FAT バッファの再読み込みや DPB の再構築を行う。

|項目|内容|
|-|-|
|入力 A|ドライブ番号（インターフェース内）|
|入力 B|0|
|入力 C|メディア ID（現在の DPB の値）|
|入力 HL|そのドライブの DPB の先頭アドレス|
|出力 B|1 = 交換されていない、0 = 不明、FFH = 交換された|
|出力 Cy＋A|判定そのものができない場合のエラー（A = エラーコード）|

戻り値 B の 3 状態がこのエントリーの肝である。実機（F1XDJ）の実装は次のように判定している。

1. ドライブを選択し、FDC 側の交換センス信号（ドライブ制御ラッチの読み出し bit2）を見て「交換されていない」と断定できれば、B = 1 で即座に戻る
2. 断定できない場合は、FAT の先頭セクタ（論理セクタ 1）を $SECBUF（F34DH）へ自らの DSKIO で読み、その先頭バイト（メディアバイト）を調べる。F8H〜FBH の範囲外ならエラー（Cy セット、A = 10）
3. GETDPB を呼んで DPB を再構築し、読み取ったメディアバイトと入力 C（交換前のメディア ID）を比べる。一致すれば B = 0（不明だがメディアは同じ）、異なれば B = FFH（交換された）

「不明（0）」は、カーネルに対して「FAT を読み直せ」という指示として働く。交換検出のハードウェアを持たないエミュレーターでは、イメージの差し替えを検出できる場合はそれを使い、検出できない場合は常に 0 を返すのが安全な実装である。常に 1 を返すと、イメージを差し替えてもカーネルが古い FAT を使い続けてファイルを壊す危険がある。逆に常に FFH を返すと、毎回 DPB の再構築と FAT の再読み込みが走り、安全だが遅くなる。

## 4.4 GETDPB（4016H）

メディア ID から DPB を構築する。2.4 節で述べたメディアテーブルからの転送が仕事のすべてである。

|項目|内容|
|-|-|
|入力 A|ドライブ番号（インターフェース内）|
|入力 B|メディアバイト（FAT の先頭バイトの値）|
|入力 C|メディア ID|
|入力 HL|DPB の先頭アドレス|
|出力 Cy|セット = そのメディアには対応しない（エラー）|

実機の実装（両機種とも同型）は、B が F8H 未満なら Cy セットで即座にエラーとし、そうでなければメディアテーブルの (B − F8H) × 18 バイト目から 18 バイトを HL+1 へコピーする。DPB の +0（ドライブ番号）と +19〜+20（FAT ポインタ）には触らない。

ドライバが対応するメディアの種類は、このテーブルにエントリを用意した範囲に限られる。新しい形式のイメージを扱いたい場合は、テーブルへ 18 バイトのエントリを追加するだけでよい。逆に、テーブルにないメディア ID のディスクは「対応しないメディア」として正しくエラーになる。

## 4.5 CHOICE（4019H）

フォーマットの種類をユーザーに選ばせるための、メニュー文字列を返す。

|項目|内容|
|-|-|
|出力 HL|メニュー文字列（00H 終端）のアドレス。0 の場合は選択肢なし|

文字列の書式はドライバの自由である。実機の例は次のような内容である（文字列そのものではなく形式の説明として示す）。

- F1XDJ：改行に続けて「1 - 片面」「2 - 両面」の 2 行
- WSX：改行に続けて「1 - 片面・倍トラック」「2 - 両面・倍トラック」の 2 行

この文字列は、フォーマット処理の本体である FORENT（4.8 節）が RDSLT で 1 バイトずつ読みながら表示する。番号は 1 始まりで、ユーザーが入力した番号がそのまま DSKFMT の A レジスタへ渡される。単一形式しか持たないドライバでは、HL = 0 を返すことで選択を省略できる（tg45 の記述による）。

## 4.6 DSKFMT（401CH）

物理フォーマットを行う。ディスク全体の初期化（トラックへのセクタ配置、ブートセクタ・FAT・ルートディレクトリの書き込みまで）を含む。

|項目|内容|
|-|-|
|入力 A|フォーマットの種類（CHOICE の番号、1 始まり）|
|入力 D|ドライブ番号（インターフェース内）|
|入力 HL|ワークエリアの先頭アドレス|
|入力 BC|ワークエリアの長さ|
|出力 Cy|リセット = 正常終了、セット = 異常終了|
|出力 A|異常時のエラー番号|
|レジスタ|すべて破壊してよい|

実機の振る舞いから読み取れる作法は次のとおりである。

- 種類の番号が範囲外なら、A = 12 で Cy セットして即座にエラーとする（両機種共通）
- ワークエリアの長さはドライバが検査してよい。WSX は BC の上位バイトが 14H 未満（＝ 1400H バイト未満）なら A = 14 でエラーとする。tg45 は呼び出し側の作法として「8KB 程度を取ること」と述べており、ドライバは与えられた範囲だけを使う
- ワークエリアの内部はドライバの自由である。WSX は先頭にパラメータブロックを置いてフォーマット処理全体で使い回している
- 物理 1 台で論理 2 台を登録している場合、対象論理ドライブのディスクへの差し替えをユーザーに促す必要がある。WSX の DSKFMT は、ワークエリアに記録した物理台数を参照し、カーネルのプロンプトルーチン（625AH、F33FH の論理ドライブ名を表示してキー入力を待つ）を呼んでこれを行う

エミュレーター実装では、DSKFMT は「指定された種類に対応する真っ白なイメージを作成し、ブートセクタ・FAT・ルートディレクトリを初期状態で書き込む」処理になる。種類とメディア ID の対応（1 → F8H、2 → F9H のような）はドライバが決める。

## 4.7 MTROFF（401FH）と MTOFF（4029H）

401FH の役割は「自インターフェースのドライブのモーターを止める」ことである。このエントリーには資料間で名前の食い違いがあり、本書では実コードの証拠から **MTROFF** の名を採用する。経緯は次のとおりである。

- tg45 は 401FH に名前を与えず、「そのインターフェースのドライブだけを初期化（停止）する」と説明し、MTOFF の名は 4029H の入口に与えている
- ユーザー提供のジャンプテーブルニーモニック表は、401FH を MTROFF としている
- 実コードでは、401FH の飛び先はドライバ領域内にあり、F1XDJ ではドライブ制御ラッチへ全ドライブを順に選択して最後にデセレクトする値を書き（モーター停止）、WSX では FDC へモーター停止に関わるコマンドを発行する。どちらも「自インターフェースのドライブを止める」処理である
- 一方 4029H の飛び先はカーネル内の 620DH で、DRVTBL を走査して**全インターフェースの 401FH を CALSLT で順に呼ぶ**処理である。DOS2 のカーネルにも同型の処理（4CD3H）があり、やはり 401FH を呼ぶ

つまり MTOFF（4029H）は「全部止めよ」というカーネル側の配布係で、実際に止めるのは各ドライバの 401FH である。401FH の名前は MTROFF とするのが実態に合う。

なお、カーネルの MTOFF は 401FH を呼ぶ直前に、RDSLT（メイン ROM の 000CH）で同じ 401FH のバイトを読むという動作をする。理由は資料にも実コードの文脈にも明記されておらず、未確定事項として付録 A.4 に挙げる。ドライバ側にこの読み出しへの備えは不要である。

エミュレーター実装では、MTROFF は何もしなくてよい（RET のみ）。ただし「呼ばれる」こと自体はカーネルの正常な動作の一部であり、入口を用意しておく必要はある。

## 4.8 FORENT（4025H）

FORENT はフォーマットの対話処理全体を担うカーネル側の入口で、ドライバの仕事ではない。ただしドライバ実装者が DSKFMT の呼ばれ方を理解するために、その流れを記す。

入口のバイト列は `SCF` ＋ `JP 60B1H` である。キャリーフラグを立てて共通処理へ入ることが「公開入口から来た」印になっており、カーネル内部から直接 60B1H へ入る経路（その場合は先行処理が追加される）と区別される。

60B1H の処理は次のとおりである。

1. ドライブ名（A:、B:、…）の入力を促し、(F347H) の総ドライブ数と照合する
2. 対象インターフェースの CHOICE（4019H）を CALSLT で呼び、返された文字列を RDSLT で読みながら表示する
3. ユーザーの数字キー入力（1〜9）を受け付ける
4. 「ディスクを入れてください」のプロンプトを出す
5. DSKFMT（401CH）を CALSLT で呼ぶ。このとき HL と BC（ワークエリア）は、公開入口 FORENT に渡された値がそのまま引き継がれる
6. 結果を表示する。エラー時は A のコードに対応するメッセージ（カーネル内のエラー文字列表）を出す

つまり、フォーマットに関してドライバが実装するのは CHOICE と DSKFMT の 2 本だけであり、対話の進行はすべてカーネルが引き受ける。

## 4.9 4022H・GETSLT（402DH）・4030H

残りの入口はすべてカーネル側のもので、ドライバが実装するものではない。知識として要点だけを記す。

|アドレス|内容|
|-|-|
|4022H|ディスクワークエリアとフック群を初期化するカーネルルーチン（→ 5B3AH）。フックテンプレートのコピーや、ディスクエラー処理へのポインタ（F323H）の設定などを行う。ブートセクタから DOS の起動時に呼ばれる（tg45）|
|402DH GETSLT|自スロット番号を A に返す。スロットレジスタと FCC1H のテーブルから拡張スロット込みの値を算出する。INIT の中でカーネル自身が使うほか、DOS2 の下では DOS2 カートリッジ側の GETSLT が DOS2 のスロットを返すようになる（tg45）|
|4030H|HL に (F34BH)——DOS システム本体の開始アドレス——を入れて戻るインラインコード。初期化の過程で使われる|

# 第5章 DOS2 での扱い

## 5.1 DOS2 カーネルの初期化

MSX-DOS2 のカーネル（本書では ASCII 製 DOS2 カートリッジ、カーネル バージョン 2.20 の ROM で確認した）も、ディスクインターフェースの登録については DOS1 と同じ枠組みを使う。DOS2 の INIT（403CH）の流れは DOS1 の INIT と同型で、DISKID によるマスター／スレーブの判定、固定ワークエリアの初期化、DRVTBL と $DPBLIST の管理、H.RUNC へのスタブ設定まで、同じ骨格がバンク 0 の中に見える。

DOS2 カートリッジ自身も「ドライバ契約の実装者」として登録されるが、その中身は実ドライブを持たないスタブである。確認できた内容は次のとおりである。

|要素|DOS2 カートリッジの実装|
|-|-|
|DRIVES 相当（6EFBH）|L = 0 で即座に戻る（ドライブを登録しない）|
|DSKFMT 相当（6EF6H）|A = 12 ＋ Cy セット（常にエラー）|
|INIENV 相当（6F01H）|RET のみ|
|DEFDPB 相当（6EF9H〜）|ダミーの値（"VOID" の文字列を含む領域を指す）|

登録台数が 0 のため、このスタブが実際に呼ばれることはない。DOS2 が「インターフェースの枠組みに参加はするが、実ドライブは既存のディスク ROM のドライバに任せる」という設計であることが分かる。

また、DOS2 がスレーブとして初期化される経路では、DOS2 は H.RUNC（FECBH）を自 ROM へのスタブで上書きする。これは、起動の主導権を DOS2 側へ移すための仕掛けである。

## 5.2 DOS2 から見たドライバ要求

DOS2 カーネルがドライバの公開エントリーをどう使うか、ROM 全バンク（64KB）のバイト列を走査して確認した。結果は明確で、**アドレス定数として参照されているエントリーは DSKIO（4010H）と MTROFF（401FH）だけ**であった。

- DSKIO は、DOS1 のカーネルと同じ形のディスパッチ（論理ドライブ → DRVTBL 走査で局所ドライブとスロットへ変換し、LD IX,4010H ＋ CALSLT）で呼ばれる（バンク 0 の 4C9EH〜）。レジスタ規約も DOS1 と同一である
- MTROFF は、DOS1 の MTOFF（620DH）と同型の処理（4CD3H）が DRVTBL を走査して全インターフェース分を呼ぶ
- タイマ配信テーブル（FB29H）の走査も DOS1 と同型の処理（4CFEH）がある

一方、DSKCHG（4013H）、GETDPB（4016H）、CHOICE（4019H）、DSKFMT（401CH）への参照は、どのバンクにも存在しない。つまり DOS2 は、メディア交換の検出や DPB の再構築を、DOS1 のような DSKCHG／GETDPB の呼び出しでは行っていない。DOS2 の DPB にはブートセクタの情報が反映されることが MSX-Datapack に記されており、DOS2 がブートセクタの BPB（BIOS Parameter Block）を自ら解釈して DPB を構築する方式であれば、GETDPB が不要になることと整合する。ただし、その具体的な手順をこのカートリッジ ROM から確定することはできなかった。ディスクから起動する DOS2 では本体の一部が RAM 側に置かれる構成もあり得るため、本節の結論は「ASCII 製 DOS2 カートリッジの ROM 常駐部について」の範囲に限る（付録 A.4）。

ドライバ実装者の立場では、この事実は次のように読める。**DOS2 の下でも DSKIO と MTROFF の契約はそのまま生きている**。DSKCHG と GETDPB は、DOS1 のカーネルが相手のときの契約として実装しておけばよく、DOS2 専用に何か追加する必要はない。

## 5.3 DOS1 と DOS2 の違いのまとめ

|観点|DOS1|DOS2|
|-|-|-|
|インターフェース登録|INIT が DISKID／DRVTBL の枠組みで登録|同型の枠組み（DOS2 自身もスタブとして参加）|
|セクタ読み書き|DSKIO（4010H）を CALSLT で呼ぶ|同じ|
|モーター停止|MTOFF が全インターフェースの MTROFF を呼ぶ|同じ|
|タイマ配信|FB29H テーブルを H.TIMI で走査|同じ|
|メディア交換検出|DSKCHG（4013H）を呼ぶ|ROM 常駐部からは呼ばれない|
|DPB の再構築|GETDPB（4016H）を呼ぶ|ROM 常駐部からは呼ばれない（BPB 解釈による構築と整合）|
|フォーマット|FORENT → CHOICE／DSKFMT|Disk BASIC 2 側の処理が担う（ROM 内に「Format complete」等の文字列が見える）|

## 5.4 tg45 の注意書きの読み方

tg45 には「MSX-DOS2 の環境で 4010H などの入口を直接呼ぶと、通常はエラーが返るだけである（turboR は例外）」という趣旨の注意書きがある。これはドライバ契約の否定ではない、と本書では解釈する。

公開エントリーテーブルはカーネルとドライバの間の内部境界であり、アプリケーションが直接叩くための API ではない。DOS2 の環境ではカーネルの役割を DOS2 が担っており、アプリケーションは PHYDIO（0144H）や BDOS 経由でディスクへアクセスすべきである——というのが注意書きの実質である。実際、第 5.2 節で見たとおり DOS2 のカーネル自身は DSKIO を正規の手順で使い続けている。

turboR で事情が異なるのは、DOS2 が本体に内蔵され、ディスク ROM との関係がカートリッジ版とは異なるためと tg45 は述べている。本書では turboR の ROM を検証対象にしていないため、この点は tg45 の記述として紹介するに留める。

# 第6章 ドライバ実装の指針

## 6.1 最小実装のチェックリスト

新しいディスクドライバ（ディスクドライブエミュレーターを含む）が DOS カーネルから使えるようになるために必要な要素を、第 3 章と第 4 章の契約からチェックリストとしてまとめる。

**ROM 側の定数とテーブル**

- [ ] MYSIZE：ドライバワークエリアのバイト数（実機は 9 と 26。状態を持つなら必要な分だけ宣言する）
- [ ] SECLEN：最大セクタ長（通常は 0200H）
- [ ] DEFDPB：デフォルト DPB の 21 バイトテンプレート。メディア F9H のエントリを核にし、先頭にドライブ番号 0、末尾に 2 バイトの余白（後で FAT ポインタが書かれる領域と重ならないよう、コピー元としての形を整える）
- [ ] メディアテーブル：対応するメディア ID ごとに 18 バイトのエントリ（DPB の +1〜+18）

**初期化ルーチン（カーネルから呼ばれる）**

- [ ] INIHRD：ハードウェアの初期化。ワークエリア確保前に呼ばれる点に注意し、その時点ではワークエリアへ書かない
- [ ] DRIVES：Z フラグ（CONTROL キー）を見て、戻り値 L に論理ドライブ数を返す。物理台数はワークエリアの私用フィールドに記録する。物理 1 台でも通常は L = 2（2 ドライブシミュレーション）。AF を保存する
- [ ] INIENV：ワークエリアの初期化と、タイマ配信テーブル（FB29H）へのルーチン登録。モーター管理が不要でも RET だけのルーチンを登録する
- [ ] OEMSTA：OEM 固有ステートメントがなければ `SCF; RET` のスタブでよい（実機の両ドライバともこの形）

**公開エントリー（4010H〜401FH）**

- [ ] DSKIO（4010H）：PHYDIO 規約どおりの読み書き。失敗時は Cy セット＋A にエラーコード、B に残りセクタ数
- [ ] DSKCHG（4013H）：交換検出。検出手段がなければ B = 0（不明）を返すのが安全側の実装
- [ ] GETDPB（4016H）：メディアテーブルから DPB+1 へ 18 バイト転送。メディアバイトが F8H 未満なら Cy セットでエラー
- [ ] CHOICE（4019H）：メニュー文字列へのポインタを HL に返す。単一形式なら HL = 0 でもよい
- [ ] DSKFMT（401CH）：種類の範囲検査と、ワークエリア長（HL／BC）の範囲内での作業。範囲外の種類は A = 12 でエラー
- [ ] MTROFF（401FH）：モーター停止。エミュレーターでは RET のみでよい

**やってはいけないこと**

- カーネルのワークエリア（DRVTBL、$DPBLIST、DPB の +0 と +19〜+20 など、カーネル管理のフィールド）をドライバから書き換えない
- DSKCHG で常に B = 1（交換なし）を返さない。イメージ差し替えを検出できない実装では特に危険で、カーネルが古い FAT を使い続け、メディアの内容を破壊しうる
- DRIVES で物理台数そのものをそのまま返さない（2 ドライブシミュレーションが効かなくなる。意図して無効化する場合は別である）

## 6.2 FDC インターフェースの違い

境界の内側にある FDC の違いが、ドライバ内部のどこに現れるかを、2 機種の対比で示す。新しいハードウェア向けにドライバを書く際の参考である。

|観点|F1XDJ（WD2793）|WSX（TC8566AF）|
|-|-|-|
|レジスタ配置|7FF8H = コマンド／ステータス、7FF9H = トラック、7FFBH = データ、7FFCH = セクタ、7FFDH = ドライブ制御ラッチ、7FFFH = 転送ポーリング|7FF8H = コマンド、7FF9H = パラメータ、7FFAH = ステータス、7FFBH = データ|
|コマンドの出し方|コマンドレジスタへ 1 バイト書き、必要な値は各レジスタへ直接書く|コマンドの後にパラメータ列を 1 バイトずつ送る|
|ドライバの状態保持|レジスタとラッチが状態を持つため、ワークエリアは小さくて済む（MYSIZE = 9）|パラメータブロックを IX 相対で保持し、コマンドごとに組み立てる（MYSIZE = 26）|
|データ転送|7FFFH をポーリングしながら 1 バイトずつ|7FFAH をポーリングしながら 1 バイトずつ|
|ディスク交換の検出|ドライブ制御ラッチの読み出し bit2（センス信号）|FDC のステータス／センス系コマンドに依存|

要点は、FDC の流儀の違いは MYSIZE の大きさとドライバ内部の状態管理に吸収され、カーネルとの境界には一切現れないことである。エミュレーターのように FDC 自体が存在しない実装では、この層は「論理セクタ番号 → イメージファイル内のオフセット」の変換に置き換わる。

## 6.3 エミュレーター接続時の注意

ディスクドライブエミュレーターをドライバとして接続する場合に、実機ドライバとの違いが問題になりやすい点を挙げる。

- **ディスク交換の通知**：DSKCHG の B = 1 は「交換されていないことの断定」である。イメージファイルの差し替え、ファイルの更新時刻やサイズの変化など、検出できる手段があるならそれをセンス信号の代わりに使う。手段がない場合は B = 0（不明）を返し、カーネルに FAT の読み直しをさせる
- **モーターとタイマ**：実ドライブではモーターの回転・停止がアクセス遅延や交換検出に絡むが、エミュレーターでは無視してよい。MTROFF は RET、タイマ配信ルーチンも RET で問題ない
- **2 ドライブシミュレーション**：物理（仮想）ドライブが 1 台でも DRIVES で 2 を返しておくと、DOS 側の A:/B: 切り替えが有効になる。論理ドライブが切り替わる場面では、カーネルが F33FH に論理ドライブを入れてドライバを呼ぶため、DSKIO の中で「今どちらのイメージを使うべきか」を判断し、必要ならカーネルのプロンプトルーチン（625AH）で差し替えを促す作法が実機（DSKFMT）にある
- **起動メディア**：電源投入直後、カーネルはデフォルトメディア（F9H）のセクタ 0 を読む。起動用イメージは 2DD・9 セクタ形式で用意し、ブートセクタの先頭バイトが EBH または E9H であること（DOS のブートコードの条件）を満たす
- **書き込み保護**：イメージの読み取り専用属性は、DSKIO の書き込みでエラーコード 0（書き込み禁止）を返すことで表現できる

## 6.4 検証の進め方

実装したドライバの検証は、境界の契約に沿って段階を踏むのが確実である。

1. INIT が通り、DRVTBL と $DPBLIST に自ドライブが登録されること（メモリダンプで確認できる）
2. デフォルト DPB のままブートセクタが読め、DOS が起動すること
3. DSKIO の読みが正しいこと（ディレクトリ表示が化けないこと）
4. GETDPB が働き、メディアごとの容量表示が正しいこと
5. 書き込みと DSKCHG の組み合わせで、イメージ差し替え後に古い FAT が使われないこと
6. FORENT 経由のフォーマットが CHOICE → DSKFMT の順で完走すること

実機ドライバとの比較検証には、本書で使った 2 機種の ROM のような「動く実例」との差分を見る方法が有効である。特にエントリーテーブル（4010H〜4030H）のバイト列は、両機種ともカーネル部が一致する形になっているため、自作 ROM のテーブルが同じ形をしているかが最初のチェックポイントになる。

# 第7章 実働サンプル：ROM ディスクドライバ

## 7.1 全体構成

本章では、第 6 章までの契約を実際に動く形にしたサンプルを示す。既存の DiskBIOS カーネル（本書の解析対象である F1XDJ の disk ROM）のドライバ領域を差し替えて、もう一方のカートリッジスロットに入れた ROM をディスクとして見せる「ROM ディスク」である。Disk BASIC からはドライブ A: として見え、`FILES` で中身が表示でき、`LOAD` して `RUN` できる。書き込みは読み取り専用として正しくエラーになる。

サンプルは 3 つの要素からなる。

|要素|役割|
|-|-|
|カーネル|手元の disk ROM のカーネル部分（4000H〜73FFH）。差し替えない。ただし接続点だけを新しいドライバへ向け直す|
|ドライバ（romdisk.asm）|7400H〜7FFFH に収まる読み取り専用ドライバ。公開エントリー 6 本と初期化 3 本、OEMSTA を実装する|
|データ ROM|署名と小さな FAT12 イメージを持つだけの 16KB ROM。コードは持たない。メディアの実体|

配布物は次のファイルである。合成済み ROM はカーネル部分の著作権のため配布せず、合成は各自の手元の disk ROM に対して行う形にした。

|ファイル|内容|
|-|-|
|romdisk.asm|ドライバ本体（zma 記法、481 バイト）|
|build_sample.py|カーネルとドライバの合成ツール。接続点の書き換えを担当|
|make_romdisk.py|データ ROM のイメージビルダー。ファイルを入れて 16KB ROM を生成|
|demo.bas|データ ROM に収録するデモ用 BASIC プログラム|
|README.md|ビルドと実行の手順|

## 7.2 差し替えの仕組み

差し替えは、カーネル側の接続点をすべて新しいドライバへ向け直すことで行う。接続点は本書の解析で確定した 14 箇所である。

|接続点|書き換える内容|
|-|-|
|4011H／4014H／4017H／401AH／401DH／4020H|ジャンプテーブル 6 本（DSKIO／DSKCHG／GETDPB／CHOICE／DSKFMT／MTROFF）の飛び先|
|5770H／5851H／5890H|INIT 内の呼び出し 3 本（INIHRD／DRIVES／INIENV）の飛び先|
|65AFH|STATEMENT 入口の OEMSTA へのジャンプの飛び先|
|5884H|LD HL,DEFDPB のオペランド|
|5AE8H|LD A,(DEFDPB+1) のオペランド（ブート時にデフォルトメディア ID を読む箇所。見落とすと旧ドライバのテンプレートを読み続ける）|
|57AAH／581EH|MYSIZE の即値 2 箇所（LD HL,F380H+MYSIZE と LD HL,MYSIZE）|

ドライバ側は、先頭に 10 本の JP を並べたベクタテーブルを固定配置する。build_sample.py はアセンブル済みドライバのベクタテーブルを読んで接続点へ書き込むので、ドライバ内部のコード配置が変わってもツールの修正は要らない。共有している約束は「ベクタの並び順」と「DEFDPB のオフセット（1EH）」だけである。

もう 1 つの安全策として、build_sample.py は書き換え前に各接続点の元の値が想定したカーネル（F1XDJ）の値と一致することを確認し、違えば合成を中止する。想定外の ROM に無言でパッチを当てて壊れた ROM を作らないためである。合成後の検証では、接続点とドライバ領域を除いてカーネルが元の ROM とバイト単位で一致することも確認した。

なお、カーネルからドライバ領域のアドレス（7D17H 等）へ向けられたように見える参照が INIT 周辺に 4 箇所あるが、これはスロット指定の作法（CALSLT の IY に (FCC0H) を入れる形）からメイン ROM 側への参照であり、ドライバ領域への参照ではないことを確認済みである（付録 A.2）。差し替えで潰してはいけない参照は、上記の 14 箇所ですべてである。

## 7.3 DSKIO の解説

DSKIO（4.2 節）はこのドライバの中核である。仕事は「論理セクタ番号をデータ ROM 内のアドレスへ変換し、B セクタ分を RDSLT で転送する」ことに尽きるが、実装上の注意が 3 点ある。

第 1 に、入口のレジスタ退避である。ワークエリアのアドレスはカーネルの補助ルーチン（5FC2H）で得るが、これは A／BC／HL を壊す。そこで DSKIO は、まず入力レジスタをすべてスタックへ退避し、ワークエリア（IX）を確保してから入力を復元する。IX／IY 自体も呼び出し側が使うため、入口で退避し出口で戻す（4.2 節の作法）。

第 2 に、転送の途中状態はレジスタではなくワークエリアに置く。転送に使う RDSLT（メイン ROM の 000CH）は BC と DE を壊す（HL は保存される）ため、残りセクタ数・現在のセクタ番号・転送先アドレスをレジスタに保持したままループすることはできない。ワークエリアの +4〜+10 を DSKIO の作業領域として割り当て、そちらで状態を保持する。

第 3 に、アドレス変換である。イメージはデータ ROM の 4020H から始まり、総セクタ数は最大でも 31（16KB に収まる上限）である。したがってセクタ番号は 31 未満に限られ、転送元アドレスは「下位バイト = 20H、上位バイト = 40H + セクタ番号 × 2」と単純な計算で決まる。範囲検査は総セクタ数との比較（SBC）で行い、範囲外なら部分的に転送した分を進めた上で、エラーコード 8（レコードが見つからない）と残りセクタ数を返して戻る。実機ドライバの「転送できた分は進め、残りを B に残す」振る舞い（4.2 節）に合わせたものである。

読み以外の経路は次のとおりである。

- 書き込み指定（CY セット）：読み取り専用メディアとして、エラーコード 0（書き込み禁止）を返して即座に失敗する（6.3 節）。B は入力のまま＝1 セクタも書いていない、という申告になる
- 局所ドライブが 0 でない、またはデータ ROM が見つかっていない：エラーコード 2（ノットレディ）を返す

1 セクタの転送は、RDSLT を 512 回呼ぶループである。RDSLT が HL を保存することに依存し、転送先はワークエリアのポインタから毎回組み直す。バイト単位のスロット読みは決して速くないが、16KB のメディアでは実用上の問題にならない。高速化の方向は 7.7 節で述べる。

## 7.4 その他のエントリーと初期化

残りのエントリーはいずれも短い。各々の判断の根拠を示す。

|エントリー|実装|根拠|
|-|-|-|
|DSKCHG|B = 1（交換なし）で固定|ROM カートリッジは動作中に差し替わらないので断定できる。4.3 節の「常に 1 を返すな」という警告は、差し替え可能なイメージメディアに向けたもので、物理的に不変なメディアでは 1 が正しい答えになる|
|GETDPB|メディアバイトが F9H のときだけ、DEFDPB と重ねたメディアエントリを 18 バイト転送。それ以外は CY セットでエラー|メディアは 1 種だけなので、実機の (B − F8H) × 18 の索引計算ではなく一致検査で足りる。「テーブルにないメディアは対応しない」という 4.4 節の原則は同じ|
|CHOICE|HL = 0（選択肢なし）|形式は 1 種だけ。4.5 節の作法どおり|
|DSKFMT|A = 12、CY セットでエラー|ROM はフォーマットできない。種類の範囲外に対する実機の作法（4.6 節）と同じ返し方|
|MTROFF|RET のみ|モーターは無い。入口の存在自体が契約である（4.7 節）|
|OEMSTA|SCF; RET|実機の両ドライバと同じスタブ（固有ステートメントなし）|

初期化の 3 本は次のとおりである。

- **INIHRD は空（RET のみ）**。3.3 節で述べたとおり、INIHRD の時点ではワークエリアがまだ存在しない。実機ドライバはここで FDC を初期化するが、このサンプルの「ハードウェア」は他スロットの ROM であり、初期化すべきレジスタを持たない。署名の確認はワークエリアが使える INIENV で行う。空であることが、この段階の正しい実装である
- **DRIVES は L = 1 を返す**。ROM ディスク 1 台だけの構成とし、フロッピーは無くなる設計である。契約どおり AF は保存し（カーネルは戻った後も A を使う、3.4 節）、物理台数（= 1）は実機の作法に倣ってワークエリアの私用フィールド（+3）に記録する。L = 1 の帰結として、B: は存在しないドライブになる（7.6 節で確認する）
- **INIENV は 3 つの仕事をする**。ワークエリア（MYSIZE = 16 バイト）の 0 クリア（カーネルは中身を初期化しない。3.2 節）、データ ROM の走査と結果の記録、タイマ配信ルーチンの登録である。配信ルーチンは、実機の F1XDJ と同じく「カーネルの配信処理（6027H）へジャンプするセル」を 5FF6H 経由で登録する。モーター管理は無いが、登録そのものと配信の連鎖の継続は実機の作法に合わせる（3.5 節）

データ ROM の走査は、EXPTBL（FCC1H）を見ながら全スロットを巡り、4010H の署名 "ROMDISK" を RDSLT で照合する。拡張スロットのある主スロットでは副スロット 0〜3 を順に試す。走査の状態（主／副スロット番号や候補）は、RDSLT が BC／DE を壊す都合で、やはりワークエリア（+11〜+15）に置く。見つかればスロット番号と総セクタ数を記録し、総セクタ数は 16KB に収まる上限（31）で頭打ちにする。

## 7.5 データ ROM とイメージビルダー

データ ROM のレイアウトは次のとおりである。コードは持たず、INIT も登録しない（ヘッダの入口はすべて 0）。BIOS からは「何もしない ROM」として素通りされ、ドライバだけが署名を頼りに見つける。

|アドレス|内容|
|-|-|
|4000H|"AB"、入口 4 つはすべて 0、予約 6 バイト|
|4010H|署名 "ROMDISK"（7 バイト）|
|4017H|形式バージョン（1）|
|4018H|イメージの総セクタ数（2 バイト）|
|4020H|FAT12 イメージ（31 セクタ = 15,872 バイト）|

イメージのジオメトリは、ドライバ側のメディアテーブルと一致させてある。

|項目|値|
|-|-|
|セクタ長|512 バイト|
|セクタ 0|ブートセクタ|
|セクタ 1〜2|FAT × 2（各 1 セクタ）|
|セクタ 3|ルートディレクトリ（16 エントリ）|
|セクタ 4〜30|データ領域（1 クラスタ = 1 セクタ、クラスタ 2〜28）|

ブートセクタの先頭バイトは、意図して EBH／E9H にしていない。カーネルは先頭バイトが EBH か E9H のときだけブートコードへ制御を移す（3.7 節）ので、この ROM ディスクは DOS のシステムディスクではなく、電源投入時に Disk BASIC へ落ちるデータディスクとして振る舞う。BPB の各値はジオメトリと一致させて書いてある（DOS2 が BPB から DPB を組み立てる場合への備え、5.2 節）。

make_romdisk.py は、引数に渡したファイルをルートディレクトリへ登録したデータ ROM を生成する。ファイル名は 8.3 形式へ変換され、容量（27 クラスタ）を超えるとエラーになる。ディレクトリの日時には固定値を使うので、同じ入力からは常に同じ ROM が生成される。デモ用の demo.bas は、ASCII 形式の BASIC プログラムである。

```
10 PRINT "HELLO FROM ROM DISK!"
20 PRINT "THIS PROGRAM WAS LOADED FROM A"
30 PRINT "READ-ONLY ROM CARTRIDGE (DRIVE A:)."
40 END
```

ビルドと実行の手順は次のとおりである（詳細は README.md）。

```
zma romdisk.asm romdisk.bin
python3 make_romdisk.py -o romdisk_data.rom demo.bas
python3 build_sample.py --diskrom <手元の disk ROM> \
    --driver romdisk.bin --out romdisk_full.rom
```

合成 ROM をディスクインターフェースの ROM と差し替え、データ ROM をカートリッジスロットへ挿して起動すると、A: が ROM ディスクになる。

## 7.6 実行と検証

検証は fork openMSX で行った。Sony HB-F1XDJ のマシン定義を複製し、ディスク ROM の参照だけを合成 ROM へ差し替えたうえで、データ ROM をカートリッジとして挿入して起動した。結果は次のとおりで、第 3 章・第 4 章の契約が記述どおりに機能することが、初回の合成で一通り確認できた。

- Disk BASIC 1.0 が起動し、ドライブ A: が ROM ディスクになる
- `FILES "A:"` で DEMO.BAS が表示される
- `LOAD "A:DEMO.BAS"` して `RUN` すると、メッセージが表示される
- `SAVE "A:TEST.BAS"` は "Disk write protected" になる（書き込みがエラーコード 0 として正しく伝わっている）
- `FILES "B:"` は "Bad drive name" になる（DRIVES = 1 の帰結として、B: は存在しない）

![FILES と LOAD／RUN の実行画面](images/romdisk_run.png)

![SAVE が Disk write protected になる画面](images/romdisk_save.png)

![FILES "B:" が Bad drive name になる画面](images/romdisk_bdrive.png)

検証の過程で、カーネルとの契約について本書の記述と食い違う点は見つからなかった。特に、ブート時のセクタ 0 読み出し（PHYDIO 経由、デフォルトメディア F9H）が GETDPB を経ずに DSKIO だけで完結すること、DSKCHG が B = 1 を返す構成でも初回の FAT 読み込みはカーネル側の無効化印によって正しく行われることが、実地に確認できた。

## 7.7 拡張への道

このサンプルは 16KB の読み取り専用メディアに限定した最小構成である。実用へ広げる方向を、正直な見通しとともに挙げる。

- **容量**：16KB の壁はデータ ROM のページ配置によるもの。マッパー ROM（バンク切り替え）を使えば、セクタ番号からバンク番号とバンク内オフセットを計算する形に DSKIO を拡張でき、メガバイト級のメディアも扱える。署名の走査とカーネルとの契約は変わらない。フラッシュメモリや SD カードを持つインターフェースなら、DSKIO の転送先がそのデバイスドライバになるだけで、構造は同じである
- **書き込み**：書き込み可能なメディアに載せ替える場合は、DSKIO の書き込み経路を実装し、DSKCHG の「交換なし」断定をメディアの実情に合わせ直す必要がある。書き換えたのに B = 1 を返し続けると、カーネルが古い FAT を使い続けて内容を壊す（4.3 節）
- **DOS 起動**：本格的なブートセクタと MSXDOS.SYS をイメージに収録すれば、DOS のシステムディスクにもできる。その場合はブートセクタ先頭を EBH／E9H にし、ブートコードの契約（3.7 節）に従う必要がある。DOS2 で使う場合は、カーネル側が DOS2 カートリッジになる構成も考えられる（第 5 章）
- **複数ドライブ**：DRIVES で 2 を返し、データ ROM を 2 枚（あるいは 1 枚のバンク ROM の別領域）に分ければ、A:／B: の 2 ドライブ構成にもできる。局所ドライブ番号からメディアを選ぶ分岐が DSKIO に増えるだけである
- **速度**：RDSLT のバイト転送は遅い。マッパー ROM のバンクをページ 2 側へ一時的に切り替えて LDIR で転送する、といった最適化は可能だが、ページ切り替えと割り込みの相互作用に注意が要る。まずは正しく動く形を持ち、実測してから速くするのが順序である

## A.2 2 機種の差分の内訳

2 機種のディスク ROM（各 16KB）の全バイト比較では 3,066 バイトが異なり、一致率は 81.3% であった。ドライバ領域（7400H 以降）以外の差分は次のとおりで、いずれもドライバとの境界の形には影響しない版差である。

|範囲|内訳|
|-|-|
|4011H〜4021H|エントリーテーブルのジャンプ先アドレス（ドライバの配置差）|
|53D8H 付近（6 バイト）|コンソール出力系ルーチン内の 2 つのコールの順序入れ替え（片方は NOP で詰め物）。意味の差はない|
|5770H〜5891H の一部|INIT 内のドライバ呼び出し先アドレスと MYSIZE 等の定数|
|6576H〜65B0H（49 バイト）|STATEMENT 入口ブロックそのものの版差。OEM ステートメントの振り分け処理で、末尾は両機種ともドライバ側の OEMSTA へジャンプする。片方の機種では先頭に割り込み許可が 1 バイト多く、名前比較ループのコード生成がわずかに異なる。「カーネル共通部の中ほどにまとまった差分がある」という観測は、このブロックを指していた|
|6EDCH（1 バイト）|画面メッセージ表示系ルーチンの定数（12 と 13）の差|
|71D3H 付近（9 バイト）|DOS エラーメッセージ取得ルーチンの範囲チェックの書き方の差（片方は先頭に割り込み許可が付く）。意味は同一|
|5AE8H（1 バイト）|LD A,(DEFDPB+1) のオペランド（DEFDPB の配置差）|
|7FE0H 以降（30 バイト）|ROM 末尾の詰め物（00H と FFH）の差。FDC のレジスタ領域と重なる部分であり、コードとしての意味はない|

なお、差分の対象ではないが第 7 章の差し替え検証で確認した点を記録しておく。カーネル内の 597EH／59D5H／59E9H／5BD8H には、ドライバ領域のアドレス（7D17H／7D2FH／7D31H／7E14H）への参照に見えるオペランドがある。しかしこれらは CALSUB／CALSLT の呼び出しで IY に (FCC0H)（メイン ROM スロット）を入れる作法の一部であり、宛先はメイン ROM 側である。根拠は 2 つある。第 1 に、対応するアドレスの WSX 側の内容はドライバのエントリらしからぬ全く異なるコードであること。第 2 に、ドライバ領域を別実装に差し替えた第 7 章のサンプルでも、カーネルはこれらに触れることなく正常に動作したことである。

## A.3 ニーモニック表の 5AE2H 行について

ユーザー提供のジャンプテーブルニーモニック表には、5AE2H に「LD A,(DEFDPB+1)」という行がある（初期の 1DD ドライブ向けとされる行で、ほとんどのドライブでは 5AE7H と併記されている）。

本書で調べた 2 機種の ROM では、該当する命令は 5AE7H にあり、ブートセクタ読み出し処理（デフォルトメディア ID を C に入れ、PHYDIO でセクタ 0 を読み、C000H へ転送して先頭バイトを検査する）の一部であった。5AE2H はその直前の処理（(F340H) の読み出し命令の途中）にあたる。

したがって表の 5AE2H 行は、本書の 2 機種とは異なる世代のカーネル（初期の 1DD 機など）を指すものと考えられる。どちらの解釈でも「ブート時に DEFDPB のメディア ID が使われる」という実質は変わらない。この推測の裏付けは取れていないため、未確定事項にも挙げておく。
